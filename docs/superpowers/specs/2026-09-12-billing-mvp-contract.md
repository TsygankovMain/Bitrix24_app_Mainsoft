# Счёт и акт: контракт первой версии

Решения приняты 11–12.09.2026. Счёт — штатный смарт-счёт CRM Битрикс24 (`entityTypeId 31`).
Акт — отдельный документ на каждый счёт, с тем же номером и датой. Учёт выставленного ведёт
приложение: CRM не защищает от повторного выставления одних и тех же часов.

## Почему учёт у нас, а не в CRM

1. Списание уникально по паре «учётка пользователя + `bitrix_id`»: при `USE_PORTAL_SCOPING=False`
   у каждого пользователя своя копия записи. Ссылаться на `TimesheetItem.pk` нельзя.
2. Синхронизация физически удаляет записи, пропавшие в Битриксе (`timesheet_sync_service.py`).
   Поэтому документ хранит собственный снимок часов, ставки и суммы и ссылается на списание
   только по `bitrix_id`.

## Модели (Django, приложение `main`)

### PortalFeature — выключатель платных функций
`bitrix24_account` (FK) · `code` (`billing` | `bdds`) · `state` (`on` | `trial` | `off`, по умолчанию `off`)
· `trial_until` (nullable) · `updated_at` · `comment`. Уникальность: (`bitrix24_account`, `code`).
Менять — только management-командой; REST на запись нет.

### BillingDocument — выставленный документ
`bitrix24_account` (FK) · `status` (`issued` | `cancelled`) · `period_from` · `period_to`
· `company_id` · `company_name` · `our_company_id` · `our_company_name`
· `currency` (по умолчанию `RUB`) · `vat_mode` (`included` | `none`) · `vat_rate`
· `total_hours` · `total_amount`
· `crm_entity_id` (id смарт-счёта) · `crm_account_number` (номер счёта портала)
· `act_document_id` · `act_number` · `act_error` (текст последней ошибки печати акта)
· `created_by_id` · `created_at` · `cancelled_at` · `cancel_reason`.

### BillingLine — строка документа
`document` (FK) · `project_id` · `project_name` · `title` · `hours` · `rate` · `amount` · `sort`.
Количество — в часах. Состав строк задаёт вариант наполнения (см. «Варианты наполнения счёта»);
по умолчанию одна строка на задачу. `project_id` заполнен только у строки, все списания которой
из одного проекта.

### BillingEntry — потреблённые списания (снимок)
`document` (FK) · `bitrix24_account` (FK, для индекса) · `timesheet_bitrix_id` (int)
· `employee_id` · `employee_name` · `date_reflection` · `hours` · `rate_snapshot` · `amount`
· `project_id` · `task_id` · `description`.
**Частичный уникальный индекс** `(bitrix24_account, timesheet_bitrix_id)` c условием
`document.status = 'issued'` — одно списание не может попасть в два действующих документа.
Отмена документа освобождает списания.

### Фильтр (тело `preview` и `documents`)
`date_from`, `date_to`, `company_id`, `our_company_id`, `project_ids[]`, `task_ids[]`,
`employee_ids[]`, `billable_only` (по умолчанию true), `only_closed_periods`,
`exclude_invoiced` (по умолчанию true), `grouping` (`task` | `project` | `employee` | `single`).

**`grouping` необязателен.** Поля нет — вариант берётся из настройки портала
`billing_line_variant` (по умолчанию `task`), и ответ говорит об этом в `grouping_source`
(`settings`). Присланный вариант всегда сильнее настройки (`grouping_source: "request"`):
это осознанный выбор человека в мастере на один счёт. Мастер при открытии `grouping` НЕ
присылает — иначе зашитое в форму значение перебивало бы настройку, ради которой она заведена.

### Варианты наполнения счёта

Четыре, и вариант выбирается, а не зашит в код:

| `grouping` | Состав | Формулировка по умолчанию |
|---|---|---|
| `single` | одна строка на счёт, количество в часах | «Услуги по разработке и сопровождению за {месяц}» |
| `project` | строка на проект | «{услуга} по проекту „{проект}“, {месяц}» |
| `task` | строка на задачу (значение по умолчанию) | «{задача}, {месяц}» |
| `employee` | строка на сотрудника | «Работы {сотрудник}, {месяц}» |

Формулировка у КАЖДОГО варианта своя, со своим ключом настройки. Один общий шаблон не годился:
«{задача}, {месяц}» в счёте на одну строку читается как «Услуги по договору, август 2026», а
«Работы {сотрудник}» в строке на задачу оставило бы строку без описания работ.

### Наименование работ в строке

Строки по умолчанию собираются ПО ЗАДАЧАМ, и в наименовании работ стоит название задачи.
Раньше по умолчанию группировали по проектам и брали имя карточки проекта: у клиента НУОЛАБ
карточка названа по клиенту, и наименованием работ в счёте оказалось «НУОЛАБ».

- **Название задачи** берётся из справочника задач портала (`PortalTask`, актуальное имя), при
  его отсутствии — из снимка иерархии самой записи (`task_hierarchy_titles`), и только если нет
  ни того, ни другого — «Задача &lt;id&gt;».
- **Часы без задачи** идут отдельной строкой «Работы без привязки к задаче» и ставятся последними.
  Они не выбрасываются и не приписываются чужой задаче.
- **Уровень задачи** — настройка портала `billing_line_task_level`: `task` (по умолчанию, строка
  на листовую задачу) или `root` (подзадачи схлопываются в строку родителя верхнего уровня).
  Уровень влияет только на состав строк, не на сумму документа.
- **Формулировка** — настройка портала на каждый вариант: `billing_line_template` (вариант
  `task`, ключ без суффикса — под ним формулировка уже лежит в конфигурации порталов),
  `billing_line_template_project`, `billing_line_template_employee`,
  `billing_line_template_single`. Пустая настройка читается как значение по умолчанию ЭТОГО
  варианта. Подстановки — семь: `{задача}` (предмет строки: задача, а при другом варианте —
  проект, сотрудник или «Услуги по договору»), `{проект}`, `{сотрудник}`, `{услуга}`,
  `{клиент}`, `{месяц}`, `{период}`. Неизвестная подстановка остаётся в тексте видимой;
  известная без значения убирается вместе с прилипшим разделителем; пустой результат отдаёт
  предмет строки.
- **`{проект}` и `{сотрудник}` — только общие для всей строки.** Строка, собравшая часы
  нескольких проектов (одной строкой, по сотрудникам) или нескольких людей, проекта и
  сотрудника не имеет: назвать один из нескольких значило бы соврать в печатной форме, и
  `project_id` строки документа указывал бы не туда. Слот пустеет по правилу известной
  подстановки без значения.
- **`{услуга}`** — настройка портала `billing_service_name`, по умолчанию «Разработка».
  Отдельная настройка, а не слово внутри шаблонов: услуга повторяется в формулировках
  («Разработка по проекту…», «Услуги по разработке…»), и менять её правкой четырёх полей
  человек забудет.
- Тот же текст уходит товарной строкой в CRM (`productName`) и, после правок человека в
  предпросмотре, в счёт уходят именно его правки. Уровень задачи на момент выставления
  сохраняется в `filter_snapshot.task_level`.

### Ответ `preview`
`lines[]` (project_id, title, subject, hours, rate, amount) · `grouping` · `grouping_source`
(`settings` — настройка портала, `request` — выбор в мастере) · `task_level`
· `entries_count` · `total_hours` · `total_amount`
· `warnings[]` — каждое с кодом: `period_open` (месяц не закрыт), `already_invoiced` (N записей уже
выставлены и исключены), `no_rate` (нет ставки у проекта), `mixed_companies` (в отборе несколько
клиентов — выставлять нельзя).

### Утверждённые строки в `POST /api/billing/documents`

Рядом с фильтром тело может нести `lines[]` — строки, утверждённые в предпросмотре
(мастер отдаёт их в порядке предпросмотра, исключённые просто не отправляются):
`project_id`, `title`, `hours`, `rate`. Правила:

- **Исключение** строки означает, что её списания не потребляются и остаются доступными
  для следующего счёта.
- **Часы править нельзя**: строка документа обязана остаться суммой своих списаний
  (выставление части записи — вне первой версии). Завышенные часы, чужой проект,
  отрицательные значения и нарушенный порядок → `400`, код `lines_mismatch`.
- **Цена** правится, сумма пересчитывается как часы × цена; `amount` из тела игнорируется,
  сумму считает сервер. **Текст** применяется как есть, пустой — остаётся текст отбора.
- Пустой `lines[]` (исключили всё) → `400`, код `empty_selection`.
- Поля нет — строки собираются из отбора, поведение прежнее.
- Блокирующие проверки (несколько клиентов, открытый период, «уже выставлено») считаются
  по отбору целиком и до применения строк: исключением строки их не обойти.

### Ответ `documents/<id>`
Документ, строки, потреблённые списания и `drift[]` — что изменилось после выставления:
`changed` (часы или ставка отличаются от снимка), `deleted` (списания больше нет в БД).

## Правила

1. **Права.** Выставлять и отменять может админ портала или пользователь из списка «Бухгалтерия»
   в настройках приложения. Проверка на сервере, не только в интерфейсе.
2. **Подписка.** Декоратор на пишущих эндпоинтах: при `state = off` создание и печать запрещены
   (`403`, код `feature_disabled`), чтение реестра и отмена — разрешены.
3. **Закрытый период.** По умолчанию выставлять можно только за закрытые месяцы. Настройка портала
   `billing_allow_open_period` разрешает открытые, тогда `preview` возвращает предупреждение.
4. **Один клиент на документ.** Если в отборе несколько компаний — ошибка, а не молчаливое
   объединение.
5. **Ставка** берётся из снимка списания (`hourly_rate_snapshot`), при его отсутствии — из карточки
   проекта. Ставка включает НДС (`vat_mode = included`).
6. **Нумерация** — нумератор портала. Номер акта равен номеру счёта: в шаблон акта подставляется
   номер и дата счёта.
7. **Ответам REST Битрикс24 верить нельзя**: после создания счёта и строк перечитывать объект и
   сверять суммы; расхождение — ошибка выставления с понятным текстом.
8. **Идемпотентность.** Повторный `POST /api/billing/documents` с тем же набором списаний обязан
   упереться в частичный индекс и вернуть `409` с ссылкой на существующий документ, а не создать
   второй счёт.

### Шаблоны генератора документов

Проверено живьём на `nfr-mainsoft` 12.09.2026.

`crm.documentgenerator.template.list` отвечает **словарём по id**:
`{"result": {"templates": {"2": {...}}}, "total": 21}`. Поля одного шаблона: `id`, `active`,
`name`, `code`, `region`, `sort`, `createTime`, `updateTime`, `createdBy`, `updatedBy`,
`moduleId`, `numeratorId`, `withStamps`, `productsTableVariant`, `isDeleted`, `isDefault`,
`download`, `downloadMachine`. Поля **`entityTypeId` в ответе `list` НЕТ**.

**Фильтр по `entityTypeId` нельзя передавать.** `filter: {entityTypeId: 31}` возвращает
`{"templates": []}` и `total: 0` — как и `"31"`, `[31]`, `2` и любое другое значение. Без
фильтра тот же портал отдаёт 21 шаблон. Фильтр не сужал выборку, а обнулял её: печать акта
падала бы с «шаблонов нет» при живом штатном шаблоне. Фильтры `active` и `region` выборку не
меняют (21 из 21).

Привязку к сущностям отдаёт только `crm.documentgenerator.template.get`:
`{"result": {"template": {..., "entityTypeId": ["2_category_0", "16documentrealization",
"31_2"]}}}` — строка `31_2` и есть смарт-счёт (31) в воронке 2. На несуществующий id ответ
`{"error": "0", "error_description": "Шаблон не найден"}` — код ошибки `"0"`, отличить можно
только по тексту. Поэтому проверка «выбранный шаблон ещё существует» делается через `get`.

`isDefault` — **не** «шаблон по умолчанию для счёта»: на стенде он `Y` у 17 шаблонов из 21
(признак штатного шаблона своего вида). Выбор шаблона по нему делать нельзя, наружу отдаётся
как справочная подпись.

Штатные шаблоны стенда, привязанные к смарт-счёту: `ACT_RU` «Акт (Россия)» (id 2,
`numeratorId` 2, `productsTableVariant: service`) и `BILL_RU` «Счет (Россия)» (id 4,
`numeratorId` 4). Под слово «счёт» на портале подходят ещё `INVOICE_RU` (счёт-фактура) и
`UPD_RU` — поэтому шаблон счёта по названию **не угадывается**, только явный выбор.

### Настройки шаблонов

Две, не одна: `billing_act_template_id` (акт) и `billing_invoice_template_id` (печатная форма
счёта). Это два разных документа со своими шаблонами, нумераторами и отказами; один ключ
заставил бы печатать обе половины комплекта «счёт + акт» одним шаблоном.

- Ноль — «не выбран». Для акта это прежнее поведение (подбор по названию), для счёта — печать
  из приложения недоступна.
- Выбираются из списка `/api/billing/templates`, менять состав шаблона — только на портале.
- Перед сохранением выбранный шаблон проверяется живьём (`template.get`) и только если он
  изменился. Удалён — `400`, код `billing_template_not_found`. Недоступный генератор
  документов сохранению не мешает: это ответ про портал, а не про настройку.

## Что не входит в первую версию

Абонентская плата и сверхчасы, корректировочные документы, выставление части записи, УПД,
мультивалютность, обратный поток оплат, канал 1С, своя генерация DOCX/PDF, автоматическое
выставление по расписанию.

## Проверенное живьём (nfr-mainsoft, 12.09.2026)

Печать по смарт-счёту генератором документов работает. `crm.documentgenerator.document.add` с
`entityTypeId: 31` и `entityId` счёта создаёт документ и отвечает
`{"result": {"document": {...}}}` с полями `id`, `number`, `title`, `downloadUrl`,
`downloadUrlMachine`, `publicUrl`, `pdfUrl`, `values`, `products` и прочими.

- Шаблоном 2 (`ACT_RU`) по счёту создан документ 34 с номером, равным номеру счёта.
- Шаблоном 4 (`BILL_RU`) по счёту 4 (`accountNumber` «1») создан документ 36 с номером «1» —
  номер счёта, переданный в `values.DocumentNumber`, уважается, свой нумератор шаблона его не
  перебивает.
- `publicUrl` и `pdfUrl` в первом ответе приходят `null`: PDF собирается асинхронно. Пустая
  ссылка сразу после печати — не ошибка, она появляется при повторном чтении документа.

## Непроверенное

Свой шаблон акта из DOCX (`crm.documentgenerator.template.add`) живьём не создавался — путь
остаётся запасным и вызывается только по явному указанию. Печать по **отключённому** шаблону
(`active: N`) не проверялась: интерфейс о таком шаблоне предупреждает, но что именно ответит
портал, неизвестно.

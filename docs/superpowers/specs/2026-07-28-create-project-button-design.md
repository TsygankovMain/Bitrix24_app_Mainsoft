# Дизайн: кнопка «Создать проект»

- **Дата:** 2026-07-28
- **Статус:** согласован (вариант A), готов к планированию
- **Заказчик:** сотрудники забывают вручную заводить связку «компания + карточка смарт-процесса + проект в Задачах», из-за чего списания часов не привязываются к проекту.

## 1. Задача

Одно действие в приложении создаёт три связанные сущности в Битрикс24:

1. **Компанию** (`crm.company`) — выбранную из существующих или новую.
2. **Проект/группу в Задачах** (`sonet_group`).
3. **Карточку смарт-процесса проекта** (`crm.item`), связанную с первыми двумя.

## 2. Подтверждённая выполнимость

Права приложения на боевом портале (метод `scope`, проверено 2026-07-28):
`crm, task, entity, tasks, user_brief, sonet_group, tasks_extended, placement, timeman, mobile, userfieldconfig`

`crm` покрывает компанию и карточку, `sonet_group` — создание проекта. Переустановка приложения на порталах **не требуется**.

Существующий код уже вызывает `crm.item.add` (`embedded.vue`, `project-report.client.vue`), `sonet_group.get/update`, `crm.company.list`. Новыми будут только `crm.company.add` и `sonet_group.create`.

## 3. Решения заказчика

| Вопрос | Решение |
|---|---|
| Компания | Поиск среди существующих, создание — только если не нашлась |
| Состав формы | Полная карточка, без пустых полей (см. §5) |
| Частичный сбой | Созданное сохраняем, показываем статус по шагам, даём повторить |
| Размещение кнопки | Доска проектов **и** главный экран, форма общая |
| Владелец группы | Создатель — текущий сотрудник |
| Архитектура | Вариант A: оркестратор на бэкенде с идемпотентными шагами |

## 4. Архитектура (вариант A)

Один эндпоинт `POST /api/projects/create` принимает данные формы и выполняет три шага **строго по порядку** (карточка ссылается на компанию и группу).

**Каждый шаг идемпотентен: сначала ищет, потом создаёт.**

1. **Компания.** Передан `company_id` → используем. Иначе: сначала точный поиск по **ИНН** (`crm.requisite.list`, фильтр `RQ_INN` — точный, не подстрочный), потом точное совпадение по `TITLE`; найдена → берём; не найдена → `crm.company.add`.
2. **Реквизит с ИНН.** Только для компании, созданной на шаге 1. `crm.requisite.preset.list` (активные шаблоны типа «компания», порядок по `SORT`/`ID`) → для кандидата проверяем через `crm.requisite.preset.field.list`, что он поддерживает поле `RQ_INN` → `crm.requisite.add`. Идемпотентность: перед созданием проверяем, нет ли у компании реквизита с этим же ИНН.
3. **Группа.** `sonet_group.get` с фильтром по имени; найдена одна → берём; не найдено → `sonet_group.create` (`PROJECT=Y`) **под токеном текущего сотрудника — он и становится владельцем**. Отдельно назначать владельца или добавлять участников не требуется: создатель автоматически видит проект в Задачах и может списывать в него часы.
4. **Карточка.** `crm.item.list` по полю связи с группой; найдена → берём; не найдена → `crm.item.add` с полями формы + связи.

**Почему поиск начинается с ИНН.** ИНН — настоящий идентификатор юрлица, название — нет. Без этого шага компания «Ромашка» с уже существующей в портале «ООО Ромашка» (тот же ИНН, другое написание) не нашлась бы по названию, и приложение создало бы **вторую компанию с тем же ИНН** — порча данных в CRM клиента ради функции, добавленной ради порядка в данных.

**Расхождение названия обязано быть видимым.** Если по ИНН нашлась компания под другим названием, берём найденную, но возвращаем оба названия наружу **отдельными полями** (`name` — найденное, `entered_name` — введённое). Формулировку собирает интерфейс. Молча подменять введённое название чужим нельзя: человек ввёл одно, а проект уехал бы к другому.

**Проверка ИНН — состав символов и длина, без контрольной суммы.** Только обычные ASCII-цифры, длина 10 (юрлицо) или 12 (ИП). Ограничение на ASCII — не про опечатки: арабские, тайские и деванагари цифры преобразуются в число без ошибки, и без явной проверки в CRM клиента уехал бы ИНН из юникод-цифр, который выглядит числом, но не находится поиском. Контрольную сумму сознательно не проверяем — сам Битрикс её в своём интерфейсе не проверяет, и мы не строже платформы.

**Отказ шага реквизита гасит признак завершённости.** ИНН — часть результата по правилу «пустых полей не остаётся», поэтому «компания создана, реквизит нет» не считается успехом. Повтор безопасен: шаг 1 найдёт ту же компанию и вторую не создаст. Тексты ошибок различают подтверждённое отсутствие подходящего шаблона (настройка портала, повтор не поможет) и неудавшуюся проверку (временный сбой, повтор имеет смысл).

**Неоднозначность не разрешается автоматически.** Если поиск компании или группы вернул **более одного** совпадения, шаг не выполняется: ответ содержит найденные варианты и признак `ambiguous`, интерфейс просит выбрать конкретную сущность или подтвердить создание новой. Это снимает риск привязаться к чужому одноимённому проекту и делает поведение корректным независимо от того, встречаются ли на портале одноимённые проекты.

**Имена полей связи** (карточка → компания, карточка → группа) берутся из конфигурации маппинга портала (`ConfigurationService`), а не зашиваются в код: на разных порталах поля называются по-разному.

### Формат ответа

```json
{
  "company": {"status": "created|found|ambiguous|error", "id": "123", "candidates": [], "error": null},
  "group":   {"status": "created|found|ambiguous|error", "id": "45",  "candidates": [], "error": null},
  "card":    {"status": "created|found|skipped|error",   "id": "678", "error": null},
  "done": false
}
```
`skipped` у карточки означает, что предыдущий шаг не дал нужного идентификатора.

## 5. Форма и заполнение полей

**Правило заказчика: пустых полей не остаётся.** Каждое поле, которое использует приложение, либо проставляется автоматикой, либо заполняется сотрудником. Поле без источника значения в карточку не попадает.

Автозначения подставляются в форму **до** отправки и видны сотруднику — он может их изменить. Это не скрытые дефолты на бэкенде: человек видит, что уйдёт в карточку.

| Поле (`ProjectCard`) | Источник | Правило |
|---|---|---|
| `project_name` | пользователь | **обязательное** |
| `company_id`, `company_name` | пользователь | **обязательное** — выбор из CRM или создание новой |
| ИНН | пользователь | **обязательное только при создании НОВОЙ компании.** У компании, выбранной из поиска, не запрашивается и не изменяется — её реквизиты вне нашей зоны. Хранится не в `ProjectCard`, а в реквизите компании на стороне Битрикса (см. §4, шаг 2) |
| `our_legal_entity_id`, `our_legal_entity_name` | авто → пользователь | если в CRM ровно одна компания с признаком «моя» — подставляем; если их несколько — **обязательный** выбор |
| `curator_user_id`, `curator_name` | авто | текущий сотрудник; можно изменить |
| `project_start_date` | авто | сегодня; можно изменить |
| `project_end_date` | авто | дата начала **+ 1 год**; пересчитывается при смене даты начала, можно изменить |
| `project_hours_budget` | пользователь | необязательное; если не задано — остаётся пустым |
| `hourly_rate` | авто → пользователь | ставка из настроек портала; если в настройках нет — обязательное поле |
| `planned_budget_amount` | авто | `часы × ставка`, пересчитывается в форме на лету; пусто, если бюджет часов не задан |
| `project_type` | авто | «поставка» (`delivery`); переключатель, менять не обязательно |
| `budget_mode` | авто | «часы и сумма» (`hours_and_amount`) |
| `is_support` | авто | выключен; переключатель |
| `stage` | авто | начальная стадия воронки смарт-процесса |
| `is_archived` | авто | нет |
| `stage_source` | авто | `manual` |
| `last_writeoff_days` | авто | `0` |
| `project_id` | авто | идентификатор группы, созданной на шаге 2 |
| `project_item_id` | авто | идентификатор карточки, созданной на шаге 3 |

**Два поля осознанно могут остаться пустыми:** бюджет часов и производная от него плановая сумма. На момент заведения проекта сотрудник часто не знает объём, а выдуманное число попадёт в отчёты как факт. Это единственное исключение, и оно явное.

Обязательных для ввода полей в итоге три: название, компания и — только на порталах с несколькими своими юрлицами — наше юрлицо. Всё остальное либо предзаполнено, либо необязательно, поэтому форма остаётся быстрой: цель фичи — чтобы связку вообще создавали, а не чтобы форму снова избегали.

**Источник ставки по умолчанию** — настройки портала (`ConfigurationService`), а не константа в коде: на разных порталах ставка своя.

## 6. Интерфейс

Модальное окно, вызывается кнопкой с доски проектов и с главного экрана (компонент общий). После отправки — три строки статуса: «Компания ✓ · Проект ✓ · Карточка ✗». При ошибке — кнопка «Повторить», отправляющая тот же запрос: досоздаётся только недостающее. При неоднозначности — выбор из найденных вариантов. При успехе — ссылки на созданные сущности.

## 7. Данные и изоляция

- Все вызовы Битрикса идут под токеном текущего сотрудника: права проверяет сам Битрикс, своей системы прав не заводим.
- Запись в БД — через `scope_to_tenant`, как везде.
- **Ничего никогда не удаляется**, откатов нет.
- После успешного создания карточка сразу пишется в `project_card` (write-through), чтобы проект появился на доске немедленно, а не через фоновый синк: иначе сотрудник решит, что не сработало, и нажмёт повторно.

## 8. Обработка ошибок

Сбой одного шага не прерывает работу остальных там, где это возможно, и не роняет экран. Частичный результат возвращается и сохраняется. Ошибки Битрикса показываются человеку понятным текстом, а не трейсбеком.

## 9. Тесты

- Идемпотентность: повторный вызов с теми же данными не создаёт вторых сущностей.
- Частичный сбой: компания создана, группа упала → ответ содержит успех и ошибку, карточка помечена `skipped`.
- Неоднозначность: два совпадения по названию → `ambiguous`, ничего не создано.
- Поля связи берутся из конфигурации, а не из констант.
- Изоляция между порталами.
- Фронт: отправка формы, отображение статусов, повтор досоздаёт недостающее, сбой не роняет экран.

Отдельно по §5 — заполнение полей:

- Дата окончания = дата начала + 1 год; смена даты начала пересчитывает окончание; правка окончания вручную не затирается.
- Юрлицо: одна «моя компания» → подставлено автоматически; несколько → поле обязательно, отправка без него отклоняется.
- Ставка: есть в настройках портала → подставлена; нет → поле обязательно.
- Плановая сумма = часы × ставка; при пустом бюджете часов остаётся пустой, а не `0`.
- Созданная карточка не содержит пустых полей, кроме бюджета часов и плановой суммы — тест проверяет весь список из таблицы §5.

## 10. Вне объёма

Массовое создание, шаблоны проектов, добавление в группу кого-либо кроме создателя, редактирование созданного через эту же форму.

## 11. Проверить до реализации

Три пункта, которые нельзя выяснить чтением кода — все проверяются вызовами к боевому порталу на этапе планирования:

1. **Признак «моя компания»** — как называется поле в CRM портала и сколько компаний им помечено. От этого зависит, подставляется юрлицо автоматически или становится обязательным полем (§5).
2. **Ставка по умолчанию** — задана ли она в настройках портала. Если нет, поле ставки обязательно для ввода.
3. **Начальная стадия** воронки смарт-процесса проектов — её код нужен для `crm.item.add`.

# Дизайн: локальная read-model и вынос синхронизации Bitrix с критического пути

- **Дата:** 2026-07-27
- **Статус:** черновик на согласовании
- **Ветка:** `feat/sync-offload-read-model` (от `prod_2026`)
- **Связано:** инцидент `docs/incidents/2026-07-27-task-tab-slow.md`; фикс A `fix(fieldConfig)` `57a4ca3` (уже в prod_2026)

## 1. Проблема (с доказательствами)

Вкладка приложения в карточке задачи и отчёты грузятся 10–15 минут; когда чей-то синк «доезжает» — у всех становится быстро. По access-логу бэкенда (`app-logs-148361`, 09:05–15:23 UTC):

- **21 полный синк таймшитов за 6 ч.** `POST /api/sync-timesheets` синхронный, каждый тянет ВСЕ ~5984 записи (`date_from=None`). Тайминги `sync_all`: от 9 с до **16.8 мин** (1010755 мс), регулярно 10–17 мин (610/656/678/959/1010 тыс. мс). Держит 1 из 8 воркеров gunicorn всё это время. Внутри — постраничный `crm.item.list` с `read timeout=10s` и `over_limit` от Bitrix.
- **Отчёты тратят 3–7 с на `user_map`** (`[REPORT_PERF] report_* user_map=7152ms`), остальное — единицы мс. Причина: `BitrixDataService.fetch_users` кэширует в **Django LocMemCache** (per-воркер, in-memory, TTL ~5 мин) → холодные промахи по 8 воркерам (видно: 225 мс попал vs 7152 мс промах).
- **Проекты синкаются на открытии** (`projects/index.client.vue:403` `await syncProjectCards()`).

**Механизм:** несколько многоминутных синхронных синков выжирают пул из 8 воркеров → все запросы (getToken, статика `_nuxt/*` через WhiteNoise, отчёты, и статика/токен вкладки задачи) встают в очередь → «висит у всех, включая админов». «Зашёл админ — заработало» = чей-то синк доехал, прогрел БД/кэш, `invalidate_caches` отработал.

## 2. Цель / Не-цели

**Цель.** Открытие отчёта/приложения/вкладки задачи не запускает тяжёлых синков и читает из локальной БД (мгновенно). Свежесть держат фоновые механизмы + явная кнопка «Обновить». Отчёты быстрые (нет 3–7 с на пользователей).

**Не-цели.** Перенос бэкенда на свой сервер (отдельный чат). Очередь заданий (Celery/Django-Q) — не в этом объёме (см. §12). Изменение бизнес-логики отчётов.

## 3. Ключевая идея

Bitrix24 — источник истины. Локальная БД — быстрая копия («read-model») трёх доменов: **таймшиты** (`timesheet_item`), **проекты** (`project_card`), **пользователи** (новая таблица). Все экраны читают из БД. Копия держится свежей четырьмя механизмами:

1. **Write-through** — правка через приложение сразу пишется и в БД.
2. **Инкремент по `updatedTime`** — частый дешёвый фоновый синк только изменённого.
3. **Ночная полная сверка** — раз в сутки, ловит удаления/пропуски.
4. **Кнопка «Обновить»** — инкремент по требованию.

Плюс **гейт свежести** и маркер `last_<domain>_synced_at` как страховка.

## 4. Домены данных

### 4.1 Таймшиты (`timesheet_item` — есть)
Сейчас: `TimesheetSyncService.sync_all(date_from,date_to)` → `_sync_scoped` (быстро, по датам) или `_sync_full` (всё, 10 мин). Триггер `POST /api/sync-timesheets` (`views.py:1425`), синхронно, без гейта свежести.
Меняем:
- Режим **инкремент по `updatedTime`**: `crm.item.list` фильтр `>=updatedTime: last_timesheet_synced_at` минус overlap-буфер (~2 мин против сдвига часов/гонок). Тянет единицы записей.
- Удаления в инкременте не видны → ловит ночная полная сверка (существующий `_sync_full` с orphan-cleanup по `DELETE_SAFETY_RATIO`).
- Write-through: add/update/delete таймшита через приложение → upsert/remove ровно этой записи через существующий `normalize_items → _save_batch` (§5.1).

### 4.2 Проекты (`project_card` — есть)
Сейчас: `ProjectSyncService.sync(incremental_since_minutes)` уже умеет инкремент по `>updatedTime` (`project_sync_service.py:365`). Триггер `POST /api/project-board/sync` (`views.py:723`) и синк на открытии (`projects/index.client.vue:403`).
Меняем:
- Убрать синк с открытия (читать `project_card` из БД).
- Инкремент по расписанию (переиспользуем `sync(incremental_since_minutes=…)`).
- Ночная полная сверка (`sync()` без инкремента).
- Write-through при правке карточки через `/api/project-board/update*` (бэкенд там уже пишет в Bitrix — добавить upsert в `project_card`).

### 4.3 Пользователи (таблицы нет — добавляем)
Сейчас: `fetch_users` (`bitrix_data_access.py`) → `user.get`, кэш LocMemCache (per-воркер, TTL). `report_services.resolve_employee_name(user_map, …, fallback_prefix="User")` даёт «User <id>» при промахе. Фронт `useTaskTreeLoader` тянет `user.get` без пагинации (только первые 50).
Меняем:
- Новая модель `portal_user` (`bitrix_id`, `name`, `last_name`, `active`, скоуп portal/account, `updated_at`) + миграция.
- Синк юзеров: `user.get` постранично (все) → upsert в `portal_user`. По расписанию реже (юзеры меняются редко: раз в 1–3 ч) + ночью.
- `user_map` в отчётах строится из `portal_user` (мгновенно, шаред между воркерами, переживает рестарт).
- Фронт: имена сотрудников из БД-эндпоинта `/api/users` (с пагинацией) → уходит баг «только 50 / User <id>» (частично закрывает task «пагинация» для user.get).

## 5. Механизмы (детали)

### 5.1 Write-through
Сохранение таймшита сейчас идёт фронт→Bitrix напрямую (`task.vue handleSaveItem` → `crm.item.update`). После успешного ответа Bitrix фронт зовёт лёгкий endpoint `POST /api/timesheets/upsert-one {id}` → бэкенд `crm.item.get(id)` → `normalize_items` → `_save_batch` (1 элемент). Delete → `POST /api/timesheets/remove-one {id}`. Аналогично для карточек проектов через существующие `/api/project-board/update*`.
Инвариант: write-through — оптимизация; при сбое не критично (следующий инкремент/сверка починит). Нормализация — тем же конвейером, чтобы строка совпадала со строкой синка.

### 5.2 Инкремент по updatedTime
Маркер `last_<domain>_synced_at` — поле на `bitrix24account` (по одному на домен: таймшиты/проекты/юзеры). Тянуть `>=updatedTime` с overlap-буфером; обновлять маркер только по успеху синка.

### 5.3 Ночная полная сверка
Полный обход (`_sync_full` / `ProjectSyncService.sync()` / полный `user.get`) раз в сутки. Ловит удаления и всё пропущенное write-through/инкрементом.

### 5.4 Кнопка «Обновить» + индикатор
Кнопка в шапке отчёта/доски/приложения → инкремент по `updatedTime` текущего домена, синхронно (секунды), затем перечитать БД. Индикатор «данные на ЧЧ:ММ» из `last_<domain>_synced_at`.

### 5.5 Гейт свежести
На эндпоинтах синка: если `now - last_synced_at < N` (дефолт **N=3 мин**) — не идти в Bitrix, вернуть `{status:"fresh", last_synced_at, count}`. Защита от долбёжки кнопкой и повторных открытий.

## 6. Путь открытия
`embedded.vue reloadWorkspace`, `projects/index.client.vue`, отчётные страницы, `useReportGenerator` (дефолт `willSync=false`) — **не синкают**, читают БД мгновенно. Индикатор + «Обновить». `refresh_writeoff_stats` (статы карточек проектов) вынести из on-request в фон/ночную сверку.

## 7. Планировщик (мульти-портал)
`start.sh` — рядом с существующим проектным loop (`sleep 10800; sync_all_portals --scope project`) добавить:
- инкремент таймшитов+проектов каждые **~20–30 мин**: `sync_all_portals --scope timesheet --incremental` (+ проекты incremental);
- синк юзеров реже (**~1 ч**);
- ночная **полная сверка**: `--full` раз в сутки (все домены).
`run_scheduled_sync` уже идёт по всем порталам (`select_portal_accounts`), уважает `auto_sync_enabled` и advisory-замок. Добавить флаги `--incremental/--full` и `scope=users`. `--full` по нескольким порталам ночью — по очереди (замок), не параллельно (Bitrix-лимиты).

## 8. Фронтенд
- Убрать авто-синк: `embedded.vue:106`, `project-report.client.vue:362`, `projects/index.client.vue:403`; дефолт `useReportGenerator.willSync=false`.
- После сохранения — write-through upsert-one вместо полного фонового синка.

## 9. Обработка ошибок / безопасность
Graceful на сбое синка (уже есть: warning + «показаны последние данные»). Плановый синк: падение одного портала не рвёт остальные (есть). Гейт-skip → 200 c `last_synced_at`. Write-through best-effort (лог при сбое, не валит сохранение).

## 10. Тесты (TDD)
Бэкенд: инкремент-по-`updatedTime` (таймшиты/проекты/юзеры) тянет только изменённое; гейт свежести (skip при свежих / идёт при устаревших); write-through `upsert-one`/`remove-one` через нормализатор; `portal_user` синк + построение `user_map` из БД; планировщик уважает `scope`/`--incremental`/`--full` + флаг + замок; проставление `last_<domain>_synced_at`. Регресс: существующие sync-тесты зелёные. Фронт: открытие/генерация не зовут синк; «Обновить» зовёт инкремент; имена из `/api/users`.

## 11. Тюнируемые параметры (дефолты)
Инкремент-интервал **20 мин**; ночная сверка **есть** (напр. 03:00); гейт **N=3 мин**; overlap-буфер **2 мин**; синк юзеров **1 ч** + ночь.

## 12. Вне объёма
Очередь заданий (Django-Q2/Celery) для async «Обновить»/повторов/видимости статуса — при крошечных инкрементах для боли не нужна → кандидат на перенос. Отдача статики `_nuxt/*` через Caddy (не через воркеры) и +потоки gunicorn — опциональные митигации, отдельно.

## 13. Риски / миграция
- Пустая БД нового портала: до первого синка отчёт пуст → показать «идёт первичная загрузка»; первичный полный синк — по установке/первой плановой сверке.
- `updatedTime` не покрывает удаления → ночная сверка обязательна.
- БД — кэш, не истина: расхождение чинит сверка.
- Смена дефолта `willSync=false`: отчёт больше не тянет свежак сам → компенсируем индикатором «данные на ЧЧ:ММ» + кнопкой.
- Мульти-портал: инкремент/сверка крутятся по каждому порталу; следить за суммарной нагрузкой и Bitrix-лимитами.

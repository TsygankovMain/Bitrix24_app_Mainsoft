# Дизайн: скорость экрана проектов (вариант Б)

- **Дата:** 2026-07-28
- **Статус:** черновик, на согласование
- **Предшественник:** вариант А (гигиена ответа `meta`) — ветка `perf/project-references`

## 1. Задача

Экран проектов открывается минутами, отчёты — мгновенно. Причина установлена по боевым логам:

```
[_fetch_paginated] batch-offset pages=465 total=23252 method=crm.company.list
[_fetch_paginated] batch-offset pages=465 total=23252 method=crm.item.list
[_fetch_paginated] batch-offset pages=327 total=16382 method=crm.requisite.list

"GET /api/project-board/meta HTTP/1.1" 200 37877129
```

На каждое построение справочников приложение выкачивает из Битрикса **весь список компаний портала — 23 252 записи страницами по 50** — и отдаёт браузеру **37,9 МБ**. Отчёты быстрые, потому что после Фаз 1–2 читают локальную базу; экран проектов — последнее место, оставшееся на живых вызовах Битрикса.

Вариант А снял тройное дублирование в ответе и удлинил кэш. Он уменьшил симптом, но источник — сама идея «выгрузить справочник целиком» — остался.

## 2. Решение

**Экран проектов перестаёт ходить в Битрикс за справочниками. Списки для выпадающих полей строятся из локальной базы, а полный поиск по компаниям портала выносится в отдельный эндпоинт, который вызывается только когда пользователь начал печатать.**

Это тот же приём, которым уже вылечены таймшиты (Фаза 1) и пользователи (Фаза 2), просто применённый к последнему оставшемуся месту.

## 3. Что откуда берётся после изменений

| Список | Источник сейчас | Источник после |
|---|---|---|
| Компании в выпадающих полях | Битрикс, все 23 252 записи | Локальная база: компании, уже указанные в карточках проектов (`ProjectCard.company_id/company_name`) |
| Компании, которых ещё нет в проектах | — | Новый эндпоинт поиска, вызывается по мере ввода |
| Сотрудники (кураторы) | Битрикс, `user.get` постранично | Локальная таблица `PortalUser` (заведена в Фазе 2) |
| Свои юрлица | Битрикс, все 23 252 записи с фильтрацией в Python | Битрикс, `crm.company.list` с **серверным** фильтром `IS_MY_COMPANY=Y` — единицы записей, один запрос |
| Стадии воронки | Битрикс, небольшой ответ | Без изменений |

Ключевое: механизм «компании из карточек проектов» уже написан — метод `_get_project_card_fallback_options("company_id", "company_name")` (`project_board_service.py:669`). Сейчас он используется как запасной вариант при сбое Битрикса. Он становится основным.

Точно так же `PortalUser` уже наполняется фоновым синком и используется в `_get_user_map` отчётов — нужно лишь начать читать его и здесь вместо `BitrixDataService.fetch_active_users()`.

## 4. Эндпоинт поиска компаний

```
GET /api/project-board/companies/search?q=<строка>&limit=50
```

- Запрос короче двух символов → пустой список без обращения к Битриксу.
- Поиск по названию: `crm.company.list` с фильтром `{"%TITLE": q}` и `select: ["ID", "TITLE"]`, ограничение — одна страница. **Один запрос вместо 465.**
- Если запрос состоит из цифр и его длина 10 или 12 — это похоже на ИНН: дополнительно ищем через `crm.requisite.list` с фильтром `{"%RQ_INN": q}` и подставляем найденные компании. Так сохраняется существующая возможность искать по ИНН.
- Результат кэшируется на пару минут по паре «аккаунт + строка запроса»: пользователь набирает текст посимвольно, и повторные запросы неизбежны.
- Ответ: `{"companies": [{"id": "...", "name": "...", "inn": "..."}], "truncated": true|false}`. Флаг `truncated` нужен, чтобы интерфейс мог честно сказать «показаны первые 50, уточните запрос», а не делать вид, что это всё.

Ошибка Битрикса здесь не роняет экран: возвращается пустой список и пометка, что поиск временно недоступен, — выбрать из уже используемых компаний по-прежнему можно.

## 5. Интерфейс

`SearchableSelect.vue` получает необязательный режим серверного поиска: пропс с функцией поиска, задержка ввода 300 мс, состояние «идёт поиск», подсказка «начните вводить название или ИНН» при пустом запросе.

Поведение при выборе не меняется. Уже выбранное в карточке значение отображается из самой карточки, поэтому оно видно даже если компании нет в предзагруженном списке.

Там, где серверный поиск не задан, компонент работает ровно как сейчас — локальной фильтрацией. Это важно: тот же компонент используется для сотрудников, юрлиц и стадий, и их трогать не нужно.

## 6. Обратная совместимость

Форма ответа `/api/project-board/meta` не меняется — меняется только источник и объём содержимого. Правок в местах, где фронт читает `meta`, не требуется.

## 7. Ожидаемый эффект

- Открытие экрана проектов: обращений к Битриксу за справочниками — **ноль** вместо ~1250 (остаются только стадии и свои юрлица, оба — единичные быстрые запросы).
- Размер ответа `meta`: с 37,9 МБ до величины порядка сотен килобайт — он становится пропорционален числу компаний в проектах, а не числу компаний на портале.
- Нагрузка на портал клиента падает на порядки: сейчас каждое открытие экрана любым сотрудником — это больше тысячи REST-вызовов.

## 8. Что сознательно не делаем

- **Не заводим таблицу-копию справочника компаний.** Это вариант В. После Б он даёт уже немного: поиск и так укладывается в один запрос к Битриксу. Вернёмся, если поиск окажется медленным на больших порталах.
- **Не трогаем ИНН в карточках** и логику `inn-backfill` — это отдельная функция.
- **Не меняем поведение выпадающих списков сотрудников, юрлиц и стадий** — они небольшие и работают локально.

## 9. Тесты

- Поиск с запросом короче двух символов не обращается к Битриксу.
- Поиск по названию делает ровно один вызов `crm.company.list` с фильтром по подстроке, а не постраничный обход.
- Запрос из 10 или 12 цифр дополнительно ищет по ИНН; из 5 цифр — не ищет.
- Сбой Битрикса в поиске возвращает пустой список и пометку, а не 500.
- `meta` строит список компаний из карточек проектов и не вызывает Битрикс за компаниями.
- `meta` строит список сотрудников из `PortalUser` и не вызывает `user.get`.
- Свои юрлица запрашиваются с серверным фильтром `IS_MY_COMPANY`, без постраничного обхода всех компаний.
- Изоляция между порталами сохраняется во всех новых запросах к базе.
- Фронт: ввод короче двух символов не дёргает сервер; ввод с задержкой дёргает один раз, а не на каждый символ; сбой поиска не роняет форму.

## 10. Связь с кнопкой «Создать проект»

В плане `docs/superpowers/plans/2026-07-28-create-project-button.md` форма создания берёт список компаний из `/api/project-board/meta`. После этого изменения она должна использовать эндпоинт поиска — иначе новая форма будет предлагать только те компании, что уже есть в проектах, и не даст выбрать новую. Соответствующие задачи плана (7 и 8) нужно поправить перед возвратом к кнопке.

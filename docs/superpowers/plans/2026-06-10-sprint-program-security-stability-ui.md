# Программа спринтов: безопасность → надёжность → скорость и интерфейс

> **Для агентов-исполнителей:** это программный документ (карта спринтов). Перед выполнением каждого спринта создаётся детальный пошаговый план по методике `superpowers:writing-plans` (задача 0 каждого спринта) и сохраняется рядом: `docs/superpowers/plans/YYYY-MM-DD-sprint-N-<тема>.md`. Исполнение — по `superpowers:subagent-driven-development`, испытания пишутся до изменения поведения.

**Цель программы:** закрыть находки аудита 2026-06-10 по блокам 1–4 (архитектура, безопасность, скорость, интерфейс). Блок 5 (платный функционал) — вне программы, отдельное решение.

**Основание:** аудит от 2026-06-10 (5 агентов + ручная верификация двух критических находок). Вердикты: архитектура 5,5/10, безопасность 3/10 — публикация в Bitrix24 Market заблокирована тремя критическими дырами.

**Заказчик:** продакт (не программист). Отчётность по спринтам — на русском, без жаргона.

---

## Правила работы (одинаковы для всех спринтов)

1. **Спринт = фиксированный список задач + потолок токенов.** Старт спринта — только после «да» заказчика. Выход за оценку задачи в полтора раза — стоп и доклад.
2. **Волны параллельности.** Агенты в одной волне не трогают одни и те же файлы. Волна стартует после завершения предыдущей.
3. **Распределение моделей:** хайку — точечные правки по точной инструкции; соннет — стандартные задачи с испытаниями; опус — где цена ошибки высока (вход в систему, целостность данных, проектирование).
4. **Вся работа — в отдельной ветке спринта** (`sprint-1-security` и т.д.). В основную ветку — после приёмки заказчиком.
5. **Каждая задача:** испытание, подтверждающее проблему → правка → прогон испытаний → отдельная фиксация изменений (commit).
6. **Финал спринта:** агент-ревизор перепроверяет результат против целей спринта + полный прогон испытаний + отчёт заказчику (сделано / проверено / расход токенов план-факт / перенесено).
7. **Оркестратор** (основная сессия) лично выборочно перепроверяет критические изменения и не делегирует приёмку полностью.

**Ориентиры стоимости задач** (откалибровано по факту аудита, это вилки, не обещания):
хайку ≈ 30–60 тыс. токенов · соннет ≈ 80–150 тыс. · опус ≈ 150–250 тыс.

## Спринт 1 — «Закрыть дыры безопасности»

**Цель (понятная):** посторонний не может прочитать чужие данные и ключи; рядовой сотрудник не может открыть управленческие отчёты и настройки; секретов в репозитории нет. После спринта публикация в Market не заблокирована безопасностью.

**Бюджет: ~0,7–1,0 млн токенов.** Ветка: `sprint-1-security`.

| № | Задача | Модель | Волна | Оценка |
|---|--------|--------|-------|--------|
| 1.0 | Детальный пошаговый план спринта по методике | опус | 0 | ~100 тыс. |
| 1.1 | Утечка ключей через журналы запросов | соннет | 1 | ~120 тыс. |
| 1.2 | Секретные ключи из репозитория + памятка ротации | хайку | 1 | ~40 тыс. |
| 1.3 | Excel-защита + правило доверенных сайтов | соннет | 1 | ~130 тыс. |
| 1.4 | Права администратора на сервере | опус | 2 | ~220 тыс. |
| 1.5 | Ограничение частоты запросов | соннет | 3 | ~100 тыс. |
| 1.6 | Ревизия безопасности + полный прогон | соннет | 4 | ~100 тыс. |

### Карточки задач

**1.1 Утечка ключей через журналы запросов** — критическая дыра №1.
- Что: журналы запросов и системные журналы показывать только своей компании; тела запросов входа/установки не записывать в журнал (или маскировать поля с ключами); вычистить уже накопленные записи с ключами.
- Где: `backends/python/api/main/views.py` (get_request_logs ~1769, get_system_logs ~1802), `backends/python/api/main/middleware.py` (SKIPPED_PATH_PREFIXES), команда очистки данных, испытания.
- Приёмка: под учёткой компании А не видно журналов компании Б; в новых записях журнала нет ключей; в базе не осталось старых записей с ключами.

**1.2 Секретные ключи из репозитория.**
- Что: убрать файл `.env` из репозитория (из отслеживания, файл на диске остаётся), проверить `.gitignore`, обновить `.env.example` заглушками; написать памятку: владелец вручную меняет CLIENT_SECRET в Битрикс24 и ключ CloudPub (история репозитория их уже сохранила — смена обязательна).
- Приёмка: `git ls-files` не содержит `.env`; памятка по ротации лежит в `docs/`.

**1.3 Excel-защита + правило доверенных сайтов.**
- Что: (а) текст из Битрикс (названия задач/проектов, имена), начинающийся с `= + - @`, табуляции, экранировать апострофом при записи в Excel — иначе у получателя файла может выполниться формула; (б) исправить правило, какие сайты могут обращаться к серверу: сейчас шаблон пропускает поддельные домены вида `bitrix24.com.attacker.io`; (в) закрыть/убрать служебную админ-панель Django из боевой сборки.
- Где: `backends/python/api/main/report_excel.py` (записи ячеек: ~268, 282, 338, 375–384), `backends/python/api/settings.py:121–124`, `backends/python/api/urls.py`.
- Приёмка: испытание с названием задачи `=2+2` даёт в файле текст, а не формулу; поддельный домен получает отказ; админ-панель снаружи недоступна.

**1.4 Права администратора на сервере** — критическая дыра №2.
- Что: сейчас проверка «администратор или нет» есть только в интерфейсе, сервер не проверяет. Добавить признак роли в ключ доступа (выдаётся при входе), сделать серверную проверку и закрыть ею: настройки и маппинг, журналы, создание смарт-процессов, запуск синхронизаций, отладочные точки, отчёты с деньгами (потери выручки, ставки).
- Где: `backends/python/api/main/models.py` (формирование ключа, ~83; поле is_b24_user_admin уже есть), `backends/python/api/main/utils/decorators/auth_required.py` (+ новый декоратор), точки в `views.py` по списку. Заодно: тексты ошибок наружу — без внутренних подробностей (сейчас в ответ уходит traceback: auth_required.py:111, ветка установки ~570).
- Приёмка: под учёткой рядового сотрудника запросы к перечисленным точкам получают отказ «нет прав»; администратор работает как раньше; в ответах об ошибках нет внутренних подробностей.
- Примечание: роль берём с сервера Битрикс при входе, не с клиента — иначе подделают.

**1.5 Ограничение частоты запросов.**
- Что: ограничить частоту обращений к точке входа (получение ключа) и к тяжёлым операциям (синхронизации, выгрузки) — защита от перебора и случайной перегрузки.
- Где: `views.py` (getToken, sync-точки, выгрузки), настройка хранилища счётчиков.
- Приёмка: испытание «N запросов подряд» получает отказ с понятным сообщением после порога.

**1.6 Ревизия.** Отдельный агент с программой аудита безопасности из заключения перепроверяет пункты 1.1–1.5 по коду + полный прогон всех испытаний проекта. Результат — короткий отчёт «закрыто / не закрыто».

## Спринт 2 — «Надёжность синхронизации и скорость отчётов»

**Цель (понятная):** данные не теряются и не задваиваются даже при сбоях и одновременных запусках; отчёты формируются заметно быстрее; об ошибках синхронизации сообщается честно, а не «всё хорошо».

**Бюджет: ~1,0–1,4 млн токенов.** Ветка: `sprint-2-sync-reliability`.

| № | Задача | Модель | Волна | Оценка |
|---|--------|--------|-------|--------|
| 2.0 | Детальный план спринта | опус | 0 | ~120 тыс. |
| 2.1 | Защита от массового удаления записей при сбое | опус | 1 | ~180 тыс. |
| 2.2 | Замок от одновременных запусков синхронизации | опус | 2 | ~180 тыс. |
| 2.3 | Честные сообщения об ошибках синхронизации | соннет | 2 | ~120 тыс. |
| 2.4 | Кэш справочника сотрудников | соннет | 1 | ~110 тыс. |
| 2.5 | Мелкие ускорения отчётов | хайку | 1 | ~50 тыс. |
| 2.6 | Испытания синхронизации на настоящей базе | опус | 3 | ~230 тыс. |
| 2.7 | Защита от двойного нажатия «Сформировать» | хайку | 1 | ~50 тыс. |
| 2.8 | Ревизия спринта | соннет | 4 | ~100 тыс. |

### Карточки задач

**2.1 Защита от массового удаления.** Полная синхронизация сверяет записи с Битрикс и удаляет «лишние»; при кратковременном пустом ответе Битрикс она может удалить настоящие данные. Добавить порог разумности: если собрано подозрительно мало записей по сравнению с базой — удаление отменить и сообщить. Где: `backends/python/api/main/timesheet_sync_service.py:177–184` (образец защиты уже есть в строке 338). Приёмка: испытание «Битрикс вернул пустую страницу на середине» — записи целы.

**2.2 Замок от одновременных запусков.** Два одновременных нажатия «Синхронизировать» (или синхронизация + сохранение настроек) сейчас работают наперегонки по одним данным. Поставить замок на уровне базы по компании: второй запуск сразу получает «уже выполняется». Где: `timesheet_sync_service.py`, `project_sync_service.py`, точки запуска в `views.py:697, 1370, 1518`. Приёмка: испытание с двумя параллельными запусками — выполняется один, второй вежливо отклонён.

**2.3 Честные сообщения об ошибках.** Сейчас при сбое синхронизации сервер отвечает «успешно» со скрытой пометкой, интерфейс пометку не читает — человек работает на устаревших данных, не зная об этом. Сервер: возвращать честный статус; интерфейс: показывать «синхронизация не удалась, данные от такого-то времени». Где: `views.py:1395–1406`, `frontend/app/stores/api.ts:560–570`, страницы отчётов. Приёмка: имитация сбоя — пользователь видит понятное предупреждение.

**2.4 Кэш справочника сотрудников.** Каждый отчёт сейчас ходит в Битрикс за списком сотрудников и ждёт ответа — это главный тормоз отчётов. Хранить список в быстрой памяти сервера 15–20 минут (образец уже есть в `bitrix_data_access.py:89–150`). Где: `views.py:128–135`. Приёмка: повторный отчёт не обращается к Битрикс за сотрудниками; замер «до/после» в испытании.

**2.5 Мелкие ускорения.** (а) Список архивных проектов считать один раз и хранить в быстрой памяти, а не три подзапроса на каждый отчёт (`report_queries.py:38–44`); (б) при сборке заголовков проектов забирать из базы только три нужных поля, а не всю карточку (`report_queries.py:71–83`).

**2.6 Испытания синхронизации на настоящей базе.** Сейчас испытания синхронизации подменяют и базу, и транзакции — реальные сценарии не покрыты. Добавить испытания на настоящей (тестовой) базе: повторный запуск без дублей; сбой на середине; параллельный запуск; защита от массового удаления (2.1). Это страховка всего спринта и будущих правок. Где: новые `tests_sync_integration.py` в `backends/python/api/main/`.

**2.7 Двойное нажатие «Сформировать».** Сейчас повторное нажатие запускает второй полный цикл «синхронизация + отчёт». Отменять устаревший запрос и не дёргать синхронизацию, если фильтры не менялись. Где: `frontend/app/composables/useReportGenerator.ts:55–69`, `stores/api.ts`.

## Спринт 3 — «Интерфейс сотрудника и свежие данные без кнопки»

**Цель (понятная):** главный экран (ввод времени в задаче) выглядит и ведёт себя как родной Битрикс; фильтры отчётов не сбрасываются; данные обновляются сами по расписанию; готов проект главной перестройки хранения (одна компания — одно хранилище).

**Бюджет: ~1,0–1,5 млн токенов.** Ветка: `sprint-3-ui-freshness`.

| № | Задача | Модель | Волна | Оценка |
|---|--------|--------|-------|--------|
| 3.0 | Детальный план спринта | опус | 0 | ~120 тыс. |
| 3.1 | Экран ввода времени — на фирменные компоненты | соннет ×2 | 1→2 | ~260 тыс. |
| 3.2 | Фильтры отчётов запоминаются | соннет | 1 | ~110 тыс. |
| 3.3 | Один индикатор загрузки на «Проверке данных» | хайку | 1 | ~40 тыс. |
| 3.4 | Удобство таблиц и единый календарь периода | хайку | 2 | ~60 тыс. |
| 3.5 | Excel: экономная запись и предохранитель объёма | соннет | 2 | ~120 тыс. |
| 3.6 | Автоматическая синхронизация по расписанию | опус | 2 | ~230 тыс. |
| 3.7 | Проект перестройки «одна компания — одно хранилище» | опус | 3 | ~180 тыс. |
| 3.8 | Ревизия спринта + общий прогон | соннет | 4 | ~110 тыс. |

### Карточки задач

**3.1 Экран ввода времени.** Самый посещаемый экран не переведён на фирменные компоненты: чужие цвета (лаймовая подсветка), формы без подписей, окно редактирования не дружит с клавиатурой. Перевести на компоненты B24 (кнопки, окно, списки, переключатели) двумя заходами: сначала страница `frontend/app/pages/task.vue` (~250–344), затем `frontend/app/components/TaskGroupComponent.vue` (~196–213) и строки записей. Приёмка: визуальная сверка со страницами настроек (уже на фирменных компонентах), работа с клавиатуры, прежнее поведение записей подтверждено испытаниями.

**3.2 Фильтры отчётов запоминаются.** Сейчас период и выбор сотрудников/проектов сбрасываются при каждом переключении между 7 отчётами. Запоминать период глобально, выборки — на отчёт. Где: `frontend/app/composables/useReportFilters.ts:8–18`. Приёмка: переключение между отчётами и перезагрузка страницы сохраняют фильтры.

**3.3 Один индикатор.** На «Проверке данных» одновременно крутятся два разных индикатора загрузки. Оставить общий, научить его всем четырём состояниям. Где: `frontend/app/pages/reports/raw-data.client.vue:276–293` (убрать самописный), `components/common/ProgressOverlay.vue` (расширить сообщения).

**3.4 Таблицы и календарь.** (а) В отчётных таблицах первый уровень раскрывать сразу (сейчас отчёт выглядит пустым), строки управляются с клавиатуры; (б) поля периода — единым оформленным календарём вместо голых браузерных полей, с переносом на узком экране. Где: `components/reports/RecursiveTableRow.vue:25`, `components/common/DateRangeFilter.vue:42–43` (использовать уже существующий `UiDatePickerInput`).

**3.5 Excel-предохранитель.** Большие выгрузки собираются целиком в памяти сервера — риск падения на больших объёмах. Включить экономный режим записи и мягкий предел строк с понятным предупреждением («слишком большой период — сузьте выборку»). Где: `backends/python/api/main/report_excel.py` (точки 184, 251, 314).

**3.6 Автоматическая синхронизация.** Сейчас данные обновляются только по кнопке. Сделать фоновое обновление по расписанию (добирать только изменившееся; механизм выбрать в задаче 3.0 из вариантов: планировщик в контейнере / отдельный процесс; полноценная очередь задач — отдельным решением позже). Обязательно: журнал запусков, совместимость с замком из 2.2, отключаемость на компанию. Приёмка: записи появляются в отчётах без нажатия кнопки в пределах интервала.

**3.7 Проект перестройки хранения (только проектирование).** Сегодня копия данных создаётся на каждого пользователя компании — это умножает нагрузку и может давать разные отчёты двум руководителям. Перестройка рискованная (переезд данных), поэтому в этом спринте — только детальный проект: целевая схема «одна компания — одно хранилище», план переезда без остановки работы, план отката, оценка отдельного спринта 4. Решение о выполнении — за заказчиком.

(опубликовано: https://claude.mainsoft.su/uchet-trudozatrat/2026-09-12-product-value-ideas.md).
Порядок — его, зависимости добавлены нами.

|---|---|---|---|
| 12 | План по задаче и прогноз перерасхода | 14 + 5 ч | нужен источник плана, см. ниже |

Итого очередь: **54 ч машинной работы и 24 ч ручной**.

### 12. План по задаче и прогноз перерасхода

Читаем `timeEstimate` задач Битрикса, считаем «факт к плану» и прогноз выхода за бюджет по
текущей скорости списания. **Открытый вопрос, решить до старта:** плановые трудозатраты в
задачах почти никто не заполняет — в таком виде экран будет пустым. Предложение: читать
`timeEstimate`, а при пустом значении давать руководителю проекта вводить план в приложении
(своё поле плана по задаче). Иначе доработка мёртвая. Фолбэк на бюджет проекта уже работает.

### 7. Пакет часов и абонентская плата

Остаток предоплаченных часов по договору, сверхчасы отдельной строкой счёта, правило переноса
остатка. Спека счёта вывела это за рамки первой версии сознательно. Берём **две схемы**:
остаток сгорает и остаток переносится. Конструктор схем не строим.

### 3+2. Календарь и напоминания

Напоминание «часы не внесены» в конце дня тому, у кого ноль, и сводка руководителю в пятницу;
механика `im.notify` уже есть в `project_budget_notifier`. Но без нормы времени и
производственного календаря уведомление придёт в отпуск и в праздник, и его выключат в первую
неделю. Поэтому сначала минимальный календарь: рабочие дни, праздники, отсутствия сотрудников,
норма часов на месяц.

### Чего в очереди нет

Себестоимость и маржа, права по роли, оплаты и дебиторка, утилизация команды — остаются во
второй волне из того же документа. Права по роли стоит поднять раньше остальных: сейчас любой
сотрудник видит ставки, суммы и реестр счетов (решение от 11.06.2026 сняло серверный гейт).

## Безопасность (мелочи из ревизии спринта 1, не блокеры)

- `_redact_secrets` (middleware.py): при маскировании JSON оставляет лишнюю кавычку (`"***"`) — значение секрета вычищено, но строка лога перестаёт быть валидным JSON. Косметика, на secret не влияет.
- Нет явного теста на изоляцию журнальных записей с `bitrix24_account = NULL` (поведение корректно по семантике SQL `WHERE account_id = <pk>`, но стоит зафиксировать тестом).

## Безопасность (остаток из ревизии спринта 2)

- Текст исключения (`str(e)`/`str(exc)`) всё ещё уходит клиенту в НЕсинковых эндпоинтах `views.py` (≈591 get_token 500, ≈1677 создание смарт-процесса 500, и 400-валидации 695/785/810/835/1693/1718). Sync-пути в спринте 2 закрыты; эти — отдельная security-добивка (в основном admin/валидация, ниже риском). Заменить 500-ответы на generic + `logger.exception`, у 400 оставить только осознанные пользовательские сообщения.

## UX (из ревизии спринта 2 → взять в спринт 3)

- Панель предупреждения `syncWarning` показывается только на `pages/reports/daily.client.vue`. После спринта 2 движок `useReportGenerator` корректно выставляет `syncWarning` при сбое синка для ВСЕХ отчётов, но 6 страниц (`employee`, `project`, `project-task`, `focus-analysis`, `revenue-leakage`, `time-discipline`) её не рендерят — пользователь не видит, что данные устарели. Копипаст-паттерн: деструктурировать `syncWarning` + добавить `<div v-if="syncWarning" class="ms-panel-warning">`. Кандидат в спринт 3 (UI).

### Полная tsc-строгость (необязательно)
- В проекте нет tsc-гейта (`vue-tsc` отсутствует; `npm run lint` покрывает только `utils`/`composables`). Часть ответов стора `api.ts` типизирована как `Promise<unknown>` — потребители местами обращаются к полям без сужения (не форсится ничем). При желании: добавить `vue-tsc`-проверку и типизировать ответы стора реальными интерфейсами.
- 1 предсуществующее предупреждение `vue/require-default-prop` (`components/common/SearchableSelect.vue`, `modelValue`) — не трогали (фикс default у v-model-пропа несёт лёгкий риск поведения).

### Тёмная тема (отложено в отдельный спринт)
- Замер: ~750+ зашитых светлых утилит (`bg-white`/`text-slate-*`/`border-slate-200`) в 42 файлах, `dark:`-вариантов 0. Включение `colorMode: true` сейчас даст «полу-тёмный» сломанный UI.
- Подход: централизовать цвета в семантические CSS-токены (`ms-*` переменные с тёмными значениями), а не россыпь `dark:`-вариантов; поэкранная проверка в обоих режимах. Решение 2026-06-01 — закрыть миграцию на светлой теме, тёмную сделать отдельно.

# Проект перестройки мультитенантности: «одна компания — одно хранилище»

> Статус: **проектный документ (спек на будущий спринт 4)**. Кода нет. Решение о выполнении — за заказчиком.
> Источник: задача 3.7 плана спринта 3 (`docs/superpowers/plans/2026-06-10-sprint-3-ui-freshness.md`). Основание — аудит 2026-06-10.

## Проблема (проверено чтением `backends/python/api/main/models.py`)

`Bitrix24Account` ключуется `unique_together = ("b24_user_id", "domain_url")` — **одна строка на каждого пользователя портала**. `member_id` (идентификатор компании/портала) хранится, но НЕ является tenant-ключом и не уникален. `TimesheetItem` и `ProjectCard` привязаны FK к `bitrix24_account` (per-user).

Следствие: при установке приложения несколькими сотрудниками одной компании каждый получает **свою копию данных**. На проде **131 аккаунт против 229 проектов** — данные дублируются и раздувают БД, а два руководителя одной компании могут видеть разные отчёты (их копии синкаются в разное время с разной полнотой).

## Целевая схема: tenant-ключ `member_id`

- Ввести модель `Portal` (`member_id` как `unique`) — общие данные портала (домен, статус, конфиг-кэш). `Bitrix24Account` остаётся «учёткой пользователя» (OAuth-токены per-user) + получает FK `portal`.
- `TimesheetItem`/`ProjectCard` перепривязать к `Portal`; `unique_together` → `(portal, bitrix_id)` / `(portal, project_id)`. Данные хранятся один раз на компанию.
- Запросы отчётов скоупить по `portal`, а не по `account` (везде, где сейчас `filter(bitrix24_account=...)`: `report_queries.py`, `timesheet_sync_service.py`, `project_*`, `views.py`).
- OAuth/токены остаются per-user; для синка берётся валидный токен представителя портала (механизм «представитель» уже заложен в авто-синке спринта 3, задача 3.6).

## Стратегия переезда без простоя (expand/contract)

- **Этап 0 — подготовка (обратносовместимо):** модель `Portal` + по одному `Portal` на каждый `member_id` (data-migration, дедуп по member_id); НУЛЛЕВЫЕ FK `portal` к 3 моделям. Прод работает по-старому.
- **Этап 1 — backfill:** проставить `portal` всем аккаунтам по `member_id`, затем `TimesheetItem.portal`/`ProjectCard.portal` от их аккаунта. Идемпотентно, батчами, в фоне.
- **Этап 2 — дедупликация:** в пределах `Portal` среди записей с одинаковым `bitrix_id` оставить одну (мастер-аккаунт / максимум данных). **До** включения `unique_together (portal, bitrix_id)` дубли обязаны быть устранены, иначе индекс упадёт. Отдельная выверенная команда с отчётом, прогон на копии прода.
- **Этап 3 — двойное чтение → переключение:** флаг `USE_PORTAL_SCOPING`; чтение по `portal` с фолбэком на `account` при пустом `portal`; затем полное переключение.
- **Этап 4 — contract:** `portal` NOT NULL; portal-версии `unique_together`; снятие старых ограничений; удаление дедуп-сирот. **Точка невозврата.**

## План отката

Каждый этап — отдельная миграция. Откат = обратная миграция + `USE_PORTAL_SCOPING=False` (мгновенно возвращает чтение на account-скоупинг, пока account-данные на месте — до Этапа 4 они НЕ удаляются). Этапы 0–3 откатываются дёшево; Этап 4 — только после длительного наблюдения.

## Риски

- Дедуп выберет неполную копию → синкнуть представителей до полноты, выбирать мастер/максимум записей.
- Уникальный индекс `(portal, bitrix_id)` упадёт на остаточных дублях → дедуп обязан пройти и быть проверен до Этапа 4.
- Расхождение токенов: синк под токеном представителя; нужен фолбэк на другого пользователя при отзыве доступа.
- Объём (103k+ записей × дубли) → батчевый backfill в окно низкой нагрузки, мониторинг блокировок Postgres.
- Отчёты «поедут», если где-то остался account-скоупинг → исчерпывающий греп `bitrix24_account=` + флаг двойного чтения.

## Оценка спринта 4

Новая модель `Portal` + FK на 3 модели + 3–4 data-migration + 2 команды (backfill, dedup) + перевод всех точек скоупинга + флаг двойного чтения + тесты на sqlite (дедуп, эквивалентность отчётов до/после) + прогон на копии прода. **~250–350 тыс. токенов, отдельный спринт 4.** Обязателен прогон на копии боевой БД перед Этапом 4.

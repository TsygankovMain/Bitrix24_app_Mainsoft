# Закрытие месяца

> Статус: **проектный документ**. Кода нет, решение о выполнении — за заказчиком.
> Составлен 31.08.2026 по итогам обсуждения. Решения заказчика зафиксированы в разделе «Принятые решения» и в тексте не оспариваются.

## Зачем

Отчёт по часам — основание для счёта клиенту. Пока месяц не закрыт, его цифры могут поехать: сотрудник допишет часы задним числом, кто-то перенесёт задачу в другой проект, и приложение честно перепишет проект во всех её карточках (механизм от 31.08.2026). После выставления акта это недопустимо.

Закрытие месяца фиксирует цифры и делает расхождение видимым, а не молчаливым.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Гранулярность | **Портал целиком.** Закрыли август — закрыт у всех проектов и сотрудников |
| Опоздавшие часы | **Требуют переоткрытия периода.** Молча не принимаются |
| Записи после закрытия | **Заморожены.** Изменению не подлежат |
| Проверка перед закрытием | **Да** (вариант А) |
| Стадия «Закрыт» в смарт-процессе | Отложено |
| Снимок отчёта как акт | Отложено |
| Двухфазное закрытие | Отложено |
| Уведомление перед закрытием | Отложено |

## Честная граница возможностей

**Приложение не может физически запретить списание часов.** Карточку можно создать и отредактировать в интерфейсе самого Битрикса, минуя нас: там наш код не выполняется.

Запрет накрывает:

- все экраны приложения — вкладка задачи, встроенный экран, отчёт по проекту (все пять точек записи переведены на бэкенд 31.08.2026);
- любые попытки записи через наш API, включая обход через устаревшую вкладку (защита версии сборки).

Физический запрет по-прежнему обеспечивают **права Битрикса** — так, как это делается сейчас. Закрытие в приложении даёт другое: замораживает цифры в отчётах, объясняет человеку причину отказа и делает опоздавшие часы видимыми.

Это не недоделка, а свойство архитектуры, и его стоит понимать до начала работ.

## Что проверяет проверка

### Блокеры (закрыть нельзя)

| Проверка | Почему блокер |
|---|---|
| Записи без проекта | Не попадут ни в один счёт, час просто потеряется |
| Задачи переехали, карточки не переписаны | Отчёт разойдётся с фактическим положением задач |
| Записи, не привязанные к задаче | Нельзя ни проверить, ни объяснить клиенту |

### Предупреждения (закрыть можно)

| Проверка | Почему не блокер |
|---|---|
| Нулевые часы | Мусор, но на сумму не влияет |
| Сотрудник не списал ни часа | Бывает законно: отпуск, больничный |
| Больше 12 часов за день у одного сотрудника | Бывает законно: аврал, выезд |
| Дубли (та же задача, дата, сотрудник, часы) | Бывает законно: два одинаковых куска работы |

Разделение принципиальное: блокеры означают, что данные **сломаны**, предупреждения — что данные **необычны**. Мешать одно с другим значит приучить нажимать «всё равно закрыть».

## Данные

```
ClosedPeriod
├── portal          FK, tenant-ключ
├── year, month     уникальны в пределах портала
├── closed_at       когда
├── closed_by       кто (b24_user_id)
├── reopened_at     null, пока не переоткрывали
├── reopened_by
├── reopen_reason   обязательна при переоткрытии
└── stats           часы/записи/проекты на момент закрытия — снимок для сверки
```

Запись считается закрытой, если её `date_reflection` попадает в закрытый период. Отдельного признака на записи **не заводим**: он разъедется с таблицей периодов при первом же переоткрытии.

Опоздавшие определяются сравнением: `source_created_at` записи позже `closed_at` её периода. Отдельного поля тоже не нужно.

## Стыковка с тем, что уже работает

Три механизма, сделанных 31.08.2026, столкнутся с закрытием. Это надо решить **до** реализации.

**1. Переписывание проекта при переносе задачи.** Задача переехала — приложение переписывает проект во всех её карточках. Карточки закрытого периода трогать нельзя.

Решение: пропускать их и показывать в отчёте о переносе отдельной строкой «N карточек в закрытых периодах не изменены». Задача окажется «разорванной» — свежие часы в новом проекте, закрытые остались в старом. **Так и должно быть:** это зафиксированная история, а не ошибка.

**2. Фоновое выравнивание расхождений.** Ищет записи, чей проект разошёлся с текущей группой задачи, и правит их. С закрытыми периодами оно войдёт в бесконечный цикл: находит, пытается переписать, получает отказ прав Битрикса, повторяет через десять минут.

Решение: исключить закрытые периоды из выборки на **нашей** стороне, а не упираться в отказ Битрикса.

**3. Резолв проекта на чтении.** Отчёт подставляет актуальный проект из справочника задач. Для закрытого периода это означало бы, что отчёт за июль меняется от переноса задачи в сентябре.

Решение: для закрытых периодов резолв не применять — брать снимок из записи.

## Порядок работ

| Этап | Содержание |
|---|---|
| 1 | Модель `ClosedPeriod` + миграция + журнал |
| 2 | Проверка перед закрытием: запросы, блокеры/предупреждения, эндпоинт |
| 3 | Запрет записи: проверка в `TimesheetWriteService` — одно место на все пять точек |
| 4 | Стыковка с переносом, выравниванием и резолвом (раздел выше) |
| 5 | Экраны: список периодов, проверка, подтверждение, переоткрытие |
| 6 | Список «поступило после закрытия» |

Этапы 1–3 дают работающий запрет. Этап 4 обязателен перед выкаткой: без него закрытие и переписывание проектов подерутся.

## Открытые вопросы

1. **Часовой пояс.** Границы месяца считаются по времени портала. У Битрикса в профиле нет смещения, только строка зоны — считать придётся самим (известная особенность, уже встречалась).
2. **Первое закрытие.** В базе данные с февраля 2026. Закрывать всё разом или начать с августа, оставив прошлое открытым навсегда?
3. **Кто админ.** `is_b24_user_admin` — это админ Битрикса. Подойдёт ли он как «тот, кто закрывает месяц», или нужен отдельный список?

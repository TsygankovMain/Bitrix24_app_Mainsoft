# Инцидент 2026-06-10: 500 на всех синхронизациях после деплоя спринта 2

**Статус:** закрыт (hotfix `83f510e` на проде в тот же день).
**Окно:** ~15:54–18:57 МСК 2026-06-10 (≈3 часа).
**Затронуто:** `POST /api/sync-timesheets` и `POST /api/project-board/sync` — 100 % запросов отдавали HTTP 500.
**Потери данных:** нет. Отчёты продолжали работать на последних сохранённых данных; блокировалось только обновление из Битрикс24.

## Симптом

После ручного деплоя спринта 2 («надёжность синхронизации») страница отчётов
в консоли браузера показывала:

```
[POST] "https://<prod>/api/sync-timesheets": 500
```

на каждой загрузке. Страницы при этом открывались — синк падал «тихо».

## Первопричина

Спринт 2 добавил advisory-замок на синхронизацию
(`backends/python/api/main/utils/decorators/sync_lock.py`):

```python
def _advisory_key(account_pk: int, scope: str) -> int:
    return (int(account_pk) << 4) | SCOPE_BITS[scope]
```

PK аккаунта (`Bitrix24Account.id`) — **UUID, 128 бит**. `int(uuid) << 4` даёт
число до 132 бит, а `pg_try_advisory_lock(key bigint)` принимает **signed
int64 (максимум 2⁶³−1 ≈ 9.2×10¹⁸)**. PostgreSQL не находил перегрузку для
такого литерала и отвечал:

```
ERROR: function pg_try_advisory_lock(numeric) does not exist
```

Исключение не является `SyncLockBusy`, поэтому пролетало мимо обработчика
замка, ловилось декоратором `@log_errors` и превращалось в HTTP 500.

## Почему не поймали до прода — три слоя тестов и смоук

1. **sqlite-тесты:** на не-PostgreSQL замок — осознанный no-op, SQL не выполняется.
2. **«PG»-тест:** мокал `connection.cursor` — реальный SQL не выполнялся.
3. **Юнит-тесты ключа:** использовали `account_pk=10` (int) — переполнение
   невозможно. Тесты закрепили неверное допущение о типе PK.
4. **Смоук после деплоя:** чеклист проверял «страницы открываются», но не
   «синк вернул `{"status": "success"}`». 500 на синке не ломает страницу
   визуально — заметен только в Network/консоли.

Локально баг тоже не всплыл: боевой синк на локальном PostgreSQL после
мержа спринта 2 не прогонялся.

## Фикс

`_advisory_key` теперь хэширует `str(pk)` в 8 байт blake2b (signed int64),
младшие 4 бита — под scope, как в исходной схеме:

```python
digest = hashlib.blake2b(str(account_pk).encode("utf-8"), digest_size=8).digest()
base = int.from_bytes(digest, "big", signed=True)
return (base & ~0xF) | SCOPE_BITS[scope]
```

Детерминирован между процессами (воркеры gunicorn, cron-команда) — в отличие
от солёного встроенного `hash()`. Коллизии аккаунтов ~2⁻⁶⁰ — приемлемо.
+4 теста в `tests_sync_lock.py` фиксируют контракт «ключ от ЛЮБОГО UUID
помещается в bigint» (красный тест воспроизводил инцидент до фикса).

Сделано в рамках инцидента:

- [x] Регрессионные тесты диапазона bigint для UUID-pk (`tests_sync_lock.py`).
- [x] В смоук-чеклисты ([DEPLOY_README](../../DEPLOY_README.md) §8,

      явная проверка успешного синка по Network, а не «страница открылась».

Правила на будущее:

1. **Код, который выполняет SQL только на PostgreSQL** (в sqlite-тестах —
   no-op или мок), до мержа в `prod_2026` обязан получить хотя бы один прогон
   на реальном PostgreSQL: `docker run --rm -e POSTGRES_PASSWORD=t postgres:16-alpine`
   + ручной вызов проблемного SQL или интеграционный тест с `DB_TYPE=postgresql`.
2. **В юнит-тестах использовать реальные типы ключей** (UUID для
   `Bitrix24Account.pk`), а не удобные литералы (`10`).
3. **Смоук после деплоя — по Network-вкладке**, а не по внешнему виду
   страниц: тихие 5xx фоновых запросов иначе не видны.

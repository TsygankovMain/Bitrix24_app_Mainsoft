## 2. Паттерн 1 — веерные запросы выжигают операционный лимит Bitrix REST ✅ устранён

> **Обновление 09.08.2026.** Механизм ниже описан верно и остаётся лучшим объяснением
> «ровно 10–15 минут». Сам паттерн устранён: `T × crm.item.list` заменён на один вызов с
> IN-фильтром, `T × tasks.task.list` — на пагинируемый обход. Подробности и цифры —
> в [разделе 9](#9-обновление-09082026--что-исправлено-в-коде).

**Приоритет на 27.07: понижен до среднего** — см. [раздел 8](#8-обновление-27072026--наблюдение-заказчика).
Объясняет длительность «ровно 10–15 минут», но **не** объясняет, почему вход администратора
чинит ситуацию: блок на метод снимается только сливом корзин, ничьим логином не снимается.
Остаётся как усилитель, не как первопричина.

### Арифметика

Пусть `T` — число задач в дереве (корневая + все подзадачи). Тогда на **одно** открытие вкладки:

- `1 × tasks.task.get`
- `T × tasks.task.list` — BFS, по одному вызову на каждого родителя
  ([useTaskTreeLoader.ts:157-200](../../frontend/app/composables/useTaskTreeLoader.ts#L157))
- `T × crm.item.list` — по одному вызову на каждую задачу, фильтр по UF-полю `TASK_ID`
  ([useTaskTreeLoader.ts:206-264](../../frontend/app/composables/useTaskTreeLoader.ts#L206))
- плюс последовательная дозагрузка страниц для задач с >50 списаний
  ([useTaskTreeLoader.ts:266-325](../../frontend/app/composables/useTaskTreeLoader.ts#L266))

Вызовы упакованы в `batch` по 50 — но это **не спасает от лимита**: по документации внешний
`batch` не учитывается в `operating`, а каждый вложенный метод проверяется по собственному лимиту.

### Лимиты (официальные, [apidocs.bitrix24.ru/limits.html](https://apidocs.bitrix24.ru/limits.html))

| Лимит | Значение | Ошибка |
|-------|----------|--------|
| Интенсивность | 2 запр/сек, корзина 50 (не-Enterprise) | HTTP 503 `QUERY_LIMIT_EXCEEDED` |
| Ресурсоёмкость | **480 сек выполнения за скользящие 10 минут**, на приложение, **отдельно по каждому методу** | HTTP 429 `OPERATION_TIME_LIMIT` |

Ответ Bitrix отдаёт `time.operating` (накопленное время метода) и `time.operating_reset_at`
(когда высвободится часть лимита) — **это наши измерительные приборы.**

### Что делает SDK при подходе к лимиту

`RestrictionManager` в `@bitrix24/b24jssdk` (конфиг по умолчанию для стандартных тарифов):

- `drainRate: 2` запр/сек, `burstLimit: 50`;
- `operatingLimit: { windowMs: 600000, limitMs: 480000, heavyPercent: 80 }`;
- **адаптивная задержка включается на 80% лимита, до 7 секунд на запрос**;
- при 429/503 — 3 ретрая с экспоненциальным backoff, затем ошибка наружу.

### Механизм деградации

1. Бюджет 480 с/10 мин — **общий на всё приложение**, а не на пользователя.
2. `crm.item.list` с фильтром по UF-полю смарт-процесса идёт по таблице `b_uts_crm_dynamic_*`;
   UF-поля Bitrix по умолчанию не индексирует → цена одного вызова растёт с объёмом списаний.
3. При `T = 20` и 0,3 с на вызов одно открытие вкладки съедает ~6 с бюджета `crm.item.list`.
   480 / 6 ≈ **80 открытий на весь портал за 10 минут** — и это без учёта отчётов, которые
   ходят в Bitrix теми же учётными данными приложения.
4. После превышения метод блокируется **до слива корзин (~10 минут)**. У всех сразу.
5. Пользователи видят спиннер и **перезагружают вкладку** → новые вызовы → блок продлевается.
   Отсюда «10–15 минут» и «иногда не загружается вообще» (после 3 ретраев SDK отдаёт ошибку).

### Что подтвердит / опровергнет

- HAR: наличие `429` + `OPERATION_TIME_LIMIT`, значения `time.operating` / `operating_reset_at`,
  фактическое число вызовов `crm.item.list` и `tasks.task.list`.
- Тест «маленькая задача vs большая»: если время растёт с размером дерева — паттерн подтверждён.
- Тест «подождать 11 минут и обновить один раз»: быстрая загрузка = слив корзин.

### Куда ведёт исправление (не в этой задаче)

Данные **уже лежат у нас в БД**: `TimesheetItem` с `task_id` и `task_hierarchy_ids`
([models.py:186](../../backends/python/api/main/models.py#L186)). Вкладка ходит в Bitrix REST
в обход собственного хранилища. Правильный вектор — один эндпоинт бэкенда на всё дерево,
плюс `crm.item.list` одним вызовом с IN-фильтром вместо N вызовов.

## 3. Паттерн 2 — бэкенд в критическом пути вкладки, а ёмкость его 8 запросов

**Приоритет: высокий.** Объясняет «иногда не загружается вообще» и всплески у всех сразу.

Из [start.sh](../../backends/python/api/start.sh):

- `gunicorn --worker-class gthread --workers 2 --threads 4` → **максимум 8 одновременных запросов**;
- `--timeout 300` → зависший запрос держит слот 5 минут, потом воркер убивается;
- в комментарии зафиксировано ограничение БД: `max_connections=25`, `connect_timeout: 3`
  ([settings.py:96](../../backends/python/api/settings.py#L96));
- в том же контейнере фоновый цикл `sync_all_portals --scope project` каждые 3 часа.

Эти же 8 слотов обслуживают:

- `/api/getToken` — **дважды на каждое открытие вкладки** (см. таблицу выше);
- отчёты и выгрузки Excel — синхронные, длинные, сами ходят в Bitrix;
- синхронизации;
- **всю статику SPA** — WhiteNoise работает внутри WSGI-приложения
  ([settings.py:115](../../backends/python/api/settings.py#L115)), отдельного nginx/CDN нет.

Достаточно двух-трёх коллег, формирующих отчёты, чтобы все 8 слотов были заняты. Вкладка задачи
при этом висит **ещё до первого обращения к Bitrix** — на `getToken`, до 300 секунд, дальше 502/504.

### Что подтвердит / опровергнет

- Открыть `https://<домен-приложения>/healthz` в соседней вкладке, пока вкладка задачи висит.
  Мгновенный ответ → бэкенд жив, дело в Паттерне 1. Долго/таймаут → Паттерн 2.
- В HAR: длительность `/api/getToken`, статусы 502/504.
- На нашей стороне: access-log gunicorn, `/api/logs/requests`, строки `[REPORT_PERF]`.

## 8. Обновление 27.07.2026 — наблюдение заказчика

> «Как только я захожу и формирую отчёт или открываю приложение — оно начинает работать

### Что это оставляет

Чинится **общее для портала состояние**, которое читают и бэкенд, и вкладка задачи.
Два кандидата.

#### ✅ Кандидат A — ПОДТВЕРЖДЁН и исправлен (фикс от 27.07.2026)

**Подтверждение уточнением заказчика:** ускоряется у всех, и отчёты, и вкладка задачи, после
входа администратора. Это ровно поведение петли ниже: `app.option` — общее хранилище на
приложение (портал), запись администратора видят все, автодетект выключается сразу у всех.

**Исправление:** `autoDetectMissingMappings` теперь выходит в самом начале, если пользователь
не администратор ([fieldConfig.ts:233](../../frontend/app/stores/fieldConfig.ts#L233)). Рядовой
сотрудник больше не платит за тяжёлый `crm.item.fields` и заведомо провальный `app.option.set`
на каждой загрузке. Регрессия закрыта тестом
[fieldConfigAutoDetect.test.ts](../../frontend/tests/fieldConfigAutoDetect.test.ts):
до фикса — красный на «сотрудник не зовёт crm.item.fields», после — 13/13 зелёных, lint EXIT=0.

**Правка безопасна by construction:** для не-администратора удалены только вызовы, чей
единственный эффект был — провалившаяся запись (никакого изменения сохранённого состояния).
Наблюдаемое состояние конфига у сотрудника до и после фикса идентично; убрана лишь потерянная
латентность. Поля, которые дозаполнял автодетект (`our_inn`, `client_inn`, `project_item_id`,
`hourly_rate_snapshot`, `task_name`), во вкладке задачи не используются — дерево строится на
`TASK_ID/EMPLOYEE/HOURS/IS_CONSIDERED/DESCRIPTION/DATE`.

**Что ещё проверить в проде:** остаётся открытым вопрос магнитуды — объясняет ли один лишний
`crm.item.fields` за загрузку все 10–15 минут сам по себе, или через накопление в
операционном лимите Bitrix (Паттерн 1) и адаптивную задержку SDK. Поэтому фикс — необходимый,
но, возможно, не единственный шаг. Зонд `/healthz` продолжаем держать (Кандидат B).

#### Кандидат B — бэкенд деградирует и «просыпается» от трафика (остаётся открытым)

`/api/getToken` стоит в критическом пути вкладки задачи (и вызывается дважды за открытие),
поэтому холодный или перегруженный бэкенд тормозит и отчёты, и вкладку одинаково. Кандидатов
на «остывание» несколько: рециклинг воркеров (`--max-requests 1000` при 2 воркерах),
`collectstatic` на каждом старте контейнера до подъёма gunicorn, перезапуски по HEALTHCHECK
(`--start-period=30s --interval=30s --retries=3`), поведение хостинга при простое.

Против кандидата: кэш Django — дефолтный `LocMemCache` (`CACHES` не объявлен нигде),
ключи вида `mainsoft:v2:{account.pk}:...` — **по пользователю**. Прогрев администратором
чужие ключи не заполняет.

### Что разделяет A и B — длительность эффекта

| Эффект живёт | Вывод |
|---|---|
| Часами / до конца дня, не зависит от простоя | Кандидат A (сохранённое состояние) |
| Тает за десятки минут простоя, возвращается от трафика | Кандидат B (прогрев процесса) |
| Держится, пока администратор работает в приложении | Кандидат B, вариант «трафик держит сервер» |

### Два замера, запущенных для проверки

1. **Зонд `/healthz`** — [scripts/probe-backend.sh](../../scripts/probe-backend.sh), раз в минуту,
   сутки. Пишет CSV с разложением по фазам; колонка `server_ms` — время раздумий сервера уже
   после установки TLS. Рост `server_ms` при ровных `connect_ms`/`tls_ms` = деградация приложения,
   а не канала. Заодно это окончательный ответ на версию «плохой интернет».
2. **Строки `[FieldConfig]` в консоли** у администратора и у сотрудника без прав администратора,
   на одной и той же задаче, два открытия подряд. Ищем `Auto-detect start`,
   `Persisted auto-detected mappings`, `Failed to persist`, `could not resolve missing mappings`.

### Дополнительный факт, найденный при разборе

`TimesheetItem` привязан к `bitrix24_account`, то есть к конкретному сотруднику, а не к порталу
([models.py:186](../../backends/python/api/main/models.py#L186), `USE_PORTAL_SCOPING=False`).
Каждый сотрудник, открывая отчёт, синхронизирует весь портал в свою копию строк
([useReportGenerator.ts:61](../../frontend/app/composables/useReportGenerator.ts#L61)).
Это не объясняет ускорение, но многократно умножает нагрузку на общий лимит Bitrix
и на восемь слотов gunicorn — то есть кормит Паттерны 1 и 2.

## 7. Порядок действий (план от 27.07.2026)

1. Разослать [инструкцию](../ИНСТРУКЦИЯ_Диагностика_вкладки_задачи.md) сотрудникам.
2. Дождаться 3–5 заполненных отчётов, из них минимум один с HAR.
3. Сопоставить с серверными логами за те же минуты.
4. Только после этого — фиксить. Порядок правок определяется тем, какой паттерн подтвердится.

**Гипотезы не чиним до подтверждения.** Правка «на всякий случай» в трёх местах сразу не даст
понять, что именно помогло.

> **Обновление 09.08.2026 — почему отступили от этого принципа.** Замеры с прода так и не
> собрались за две недели. При этом часть найденного оказалась не гипотезами, а дефектами,
> доказуемыми по коду и покрываемыми тестами: лишний запрос токена, блокирующий `user.admin`
> на каждой выдаче токена, `T` вызовов вместо одного и молчаливая потеря подзадач. Такие вещи
> чинятся независимо от того, какой паттерн окажется главным на проде.
>
> Принцип «не чинить неподтверждённое» сохраняется для того, что осталось открытым
> (Кандидат B, ёмкость бэкенда) — там правка вслепую действительно смажет картину.

## 9. Обновление 09.08.2026 — что исправлено в коде

Ревью производительности по этому документу: каждый пункт перепроверялся по текущему коду,
а не принимался на веру из разбора 27.07. Часть гипотез к тому моменту уже была закрыта
(справочник сотрудников переехал в `/api/users`, синк при открытии отчёта выключен по
умолчанию — Фазы 1 и 2 sync-offload).

### 9.1. Списания дерева — один `crm.item.list` вместо `T`

Было: по вызову `crm.item.list` на каждую задачу дерева плюс строго последовательная
дозагрузка страниц для задач с более чем 50 списаниями. Упаковка в `batch` не помогала —
операционный лимит считается отдельно по каждому вложенному методу (раздел 2).

Стало: один вызов на пачку из 50 задач через IN-фильтр `@поле: [id, ...]`. Оператор `@`
для `crm.item.list` подтверждён по apidocs и работает с UF-полями. Пагинация — keyset
(`order: {id: ASC}` + фильтр `>id`), как в бэкендовом синке: offset дорожает с ростом
`start`, а страницы могут «поехать» при параллельной записи.

**Семантика не изменилась**: тот же фильтр по тому же полю, данные по-прежнему живые из
Bitrix, а не из локальной БД. Это сознательно: вкладка задачи — экран, где часы правят,
и показывать там данные с задержкой синка (до 20 минут) нельзя.

Тест: дерево из трёх задач даёт ровно один `crm.item.list` с полным IN-фильтром;
120 списаний разбираются тремя страницами без дублей.

### 9.2. Токен — один вместо двух, `user.admin` — раз в 6 часов вместо каждого запроса

Было два независимых источника блокирующих вызовов на каждое открытие:

- `api.init()` безусловно звал `reinitToken()` → `POST /api/getToken`, а `initApp()` стоит
  в `onMounted` каждой страницы. Открытие вкладки = монтируется `index.client.vue` (токен №1),
  редирект на `/task`, монтируется `task.vue` (токен №2);
- каждый `getToken` на бэкенде синхронно ходил в Bitrix за `user.admin`, занимая один из
  восьми слотов gunicorn на время round-trip'а и расходуя общий на портал лимит метода.

Стало: гард по `exp` самого JWT (токен живёт 60 минут, обновляем за 5 минут до истечения),
параллельные вызовы схлопываются общим промисом. Просто «получать один раз» было нельзя:
обработчика 401 в приложении нет, и повторный `getToken` на каждой навигации де-факто и был
механизмом обновления токена — гард это поведение сохраняет.

Флаг администратора сверяется не чаще раза в 6 часов (`Bitrix24Account.admin_flag_checked_at`,
миграция 0019). Установка приложения сверяет принудительно. При сбое вызова отметка времени
не обновляется — иначе неудачная сверка залипала бы на весь TTL.

### 9.3. Подзадачи со второй страницы больше не теряются

См. [раздел 5](#5-отдельно-два-дефекта-найденные-попутно--оба-закрыты), пункт 2.

### 9.4. Кэш бэкенда стал общим

`CACHES` не был объявлен вовсе → Django поднимал `LocMemCache`, свой в каждом процессе.
При двух воркерах прогретый кэш видела в лучшем случае половина запросов, `--max-requests 1000`
регулярно обнулял его вместе с воркером, а четыре фоновых цикла синка — отдельные процессы
со своим пустым кэшем. Кэшем при этом обёрнуты именно дорогие обращения к Bitrix
(справочник сотрудников, поиск компаний, схема карточки проекта, пресеты реквизитов) —
около двух десятков мест.

Стало: таблица в той же БД (`django_cache`, создаётся `createcachetable` в `start.sh`).
Redis не заводили: приложение живёт одним контейнером на App Platform, отдельного сервиса
кэша в контуре нет. Промах стоит round-trip в Bitrix (сотни миллисекунд), попадание из
БД — единицы миллисекунд.

Это, кстати, аргумент против **Кандидата B** из раздела 8 в его прежнем виде: довод
«кэш по пользователю, прогрев администратором чужие ключи не заполняет» остаётся верным,
но теперь кэш хотя бы переживает смену воркера.

### Что осталось открытым

| Что | Почему не тронули |
|---|---|
| **Ёмкость бэкенда: 8 одновременных запросов** (gunicorn 2×4), и из этого же пула WhiteNoise раздаёт всю статику SPA | Требует решения по инфраструктуре: отдельная раздача статики / CDN либо другой профиль воркеров. Правка вслепую без замера с прода смажет картину |
| **Кандидат B — деградация и «пробуждение» бэкенда от трафика** | Ждёт данных зонда `/healthz` (`scripts/probe-backend.sh`) |
| **Блокирующий кросс-доменный CSS** `fonts.googleapis.com` в `<head>` | Отдельная правка: локальный хостинг шрифта либо `media="print" onload` |
| **Весь бандл SPA на вкладку задачи** (`ssr: false`, `asyncEntry: false`) | Требует разбора точек входа, не точечная правка |
| **`handleSaveItem` перезагружает всё дерево после каждой правки** | После 9.1 это один запрос вместо `T`, то есть уже недорого; локальное обновление строки — отдельная задача |

### Как проверить, что помогло

Замер на проде остаётся обязательным — код-ревью не заменяет наблюдения:

1. HAR при открытии вкладки: должно быть **по одному** `/api/getToken` и `crm.item.list`
   на пачку задач вместо веера вызовов.
2. Отсутствие `429 OPERATION_TIME_LIMIT` в ответах Bitrix.
3. Зонд `/healthz` (`scripts/probe-backend.sh`) — колонка `server_ms` при ровных
   `connect_ms`/`tls_ms` разделяет деградацию приложения и проблемы канала.

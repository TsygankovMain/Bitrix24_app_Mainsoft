# Оценка миграции на Bitrix24 UI Kit

> ⚠️ **Историческая оценка ДО миграции** (риски/плюсы/варианты), дата: 2026-06-01.
> **Миграция S0–S5 ЗАВЕРШЕНА** на светлой теме (см. [CHANGELOG](../CHANGELOG.md) и [план](../superpowers/plans/2026-06-01-b24-ui-kit-migration.md)). Бренд-лайм вытеснен Bitrix-синим, состояние «наполовину» и палитра ниже описывают исходную точку, а не текущий код.

## TL;DR

Приложение уже **наполовину на B24 UI Kit** (Button ×85, Card ×25, SidebarLayout, FormField, Alert, инпуты). Структурная вёрстка и бренд (поверхности, таблицы, KPI, гриды, модалки) — на **кастомной дизайн-системе `ms-*`** (42 класса в 49 из 53 файлов), с фирменным лаймовым акцентом `#b7ea2c`, градиентным фоном и скруглением 24–28px.

**Решение по драйверам (зафиксировано 2026-06-01):** цель — **нативный вид в Bitrix + доступность/качество UX + меньше поддержки CSS**, бренд **готовы отпустить** (принять «Air»-эстетику). При таких вводных **полная миграция на нативный вид (вариант D) оправдана** и снимает главный риск ре-скина (воспроизведение бренда поверх kit больше не нужно). Делать **фазированно** (фундамент-токены → каркас → high-value-компоненты → формы → embedded в конце), с фиксацией версии kit и визуальным чек-листом (авто-тестов на регрессии нет). См. §8.1.

---

## 1. Текущее состояние (факты)

- **Объём:** 26 страниц, 27 компонентов.
- **Уже на B24:** `B24Button` (85), `B24Card` (25), `B24SidebarLayout` (5), `B24FormField` (5), `B24Alert` (3), `Switch/Separator/App` (2), плюс единичные `Select/SelectMenu/Input/InputNumber/InputMenu/Progress/Badge/Accordion/Advice/Error`.
- **Кастом `ms-*`:** 42 класса в `app/assets/css/main.css`, используются в **49 файлах**. Это намеренный **бренд-язык** (лайм/slate, светлая тема, крупные скругления, градиентный фон) — не «голый Tailwind».
- `@import "@bitrix24/b24ui-nuxt"` уже подключён; модуль в `nuxt.config.ts`; `app/app.config.ts` имеет пустой ключ `b24ui` (точка глобальной темизации). **Тёмная тема выключена** (`colorMode: false`, принудительный `light`).
- **Установленная версия kit — фактически `2.5.3`** (в package.json диапазон `^2.0.6`). API в активной разработке.

## 2. Что умеет B24 UI Kit (релевантное)

- **Есть прямые/лучшие эквиваленты:** `Table` (на `@tanstack/vue-table` — сортировка, пагинация, виртуализация, sticky, loading, empty), `Modal`/`Drawer`/`Slideover` + `useOverlay`, `Empty` (empty-state), `Badge`/`Chip`, `Alert`/`Banner`/`Advice`, полный набор форм, `Progress`/`Skeleton`/`Tooltip`/`Toast`(+`useToast`), `Pagination`, layout-каркас (`Container`/`Page*`/`SidebarLayout`/`Dashboard*`), `Tabs`.
- **a11y** на `reka-ui` (ARIA, фокус, клавиатура), адаптивность из коробки, тёмная тема поддерживается (сейчас выключена), design tokens (CSS-переменные «Air Design System»).
- **Чего НЕТ:** отдельных KPI/Stat/Metric/Chart-компонентов; самостоятельного Segmented/Toggle-group; конфиг-переопределения палитры (цвета — семантические роли `air-*`).

## 3. Потенциальные ПЛЮСЫ

1. **Нативный вид Bitrix и консистентность с порталом** — привычный UX для пользователей B24 (приложение «своё» внутри портала).
2. **Тёмная тема из коробки** (сейчас выключена) — предпочтения/доступность.
3. **Доступность (a11y).** Наши кастомные `div`-таблицы/модалки почти наверняка имеют пробелы по ARIA/клавиатуре; компоненты kit — на `reka-ui` (корректные роли, фокус-менеджмент).
4. **Меньше кастомного CSS** — отказ от части из 42 `ms-*` = меньше точек регрессий, единый источник правды (токены).
5. **Готовые мощные компоненты бесплатно:** `Table` (сорт/пагинация/виртуализация) заметно лучше наших ручных таблиц отчётов; `Toast`/`useToast` вместо `alert()`; `useOverlay` (программные модалки); `Skeleton`; `Pagination`.
6. **Токены/адаптивность/будущее** — консистентность с платформой, проще поддерживать, темизация через переменные.
7. **Скорость будущей разработки** — собирать из готовых компонентов вместо ручной вёрстки.

## 4. Потенциальные РИСКИ / издержки

1. **Потеря фирменного стиля.** Лайм/градиент/скругление 24–28px не воспроизводятся «из коробки» (макс. именованный радиус kit — 20px; палитра — семантические роли). Бренд придётся вносить **переопределением CSS-токенов** (глобально на все компоненты) + ручными классами для частичного лайма → доп. работа, риск «обобщённо-битриксового» вида.
2. **Большая поверхность рефактора.** 49 файлов используют `ms-*`; высокориски — рекурсивные таблицы отчётов, канбан, **embedded-экран отражения времени** (его видят пользователи чаще всего). **Нет авто-тестов на визуальные регрессии.**
3. **Нет переопределения палитры в конфиге** (в отличие от Nuxt UI) — бренд только через CSS-токены; «лайм только местами» требует доп. классов.
4. **Скругления ограничены 20px** — каждый 24–28px-элемент задавать вручную, иначе «поедет».
5. **Нестабильность API v2** — документация помечена «still updating»; `^2` уже подтянул `2.0.6 → 2.5.3`. Нужна фиксация точной версии на время миграции; риск поломок при апгрейде.
6. **Рост бандла** (`@tanstack/vue-table`/`vue-virtual`, `reka-ui`, `tailwind-variants`, `@vueuse/core`).
7. **Жёсткая привязка** к Tailwind v4 / Nuxt ≥4 / reka-ui (уже есть, но углубляется — откат закрыт).
8. **Тёмная тема — отдельный проект.** Все `ms-*` light-only (хардкод `slate/white`); если нужен dark — аудит всего кастома.
9. **Поведенческие изменения.** У компонентов kit своя разметка/фокус/клавиатура → возможны тонкие изменения UX; **обязательна проверка в реальном iframe Bitrix** (особенно embedded-отражение).
10. **Альтернативная стоимость.** Это **косметика/структура, не фича-ценность**; нужна явная причина, иначе ресурс лучше — на фичи/стабильность.
11. **Кастом всё равно останется:** KPI/Stat-карточки, сегментные переключатели, графики, hero-градиент, code-block — kit не закрывает.

## 5. Варианты миграции (для оценки, без обязательств)

| Вариант | Что | Стоимость | Риск | Когда выбирать |
|---|---|---|---|---|
| **A. Статус-кво / оппортунистический** | Оставить гибрид; B24-компоненты — только для НОВОГО UI; `ms-*` не трогать | ~0 (постоянно) | низкий | Нет сильного драйвера; фокус на фичах |
| **B. Выравнивание по токенам** | Перевести цвета/радиусы/тени `ms-*` на `--ui-*`/`air`-токены, имена классов оставить → открывает тёмную тему и консистентность при минимальном изменении разметки | малая–средняя | низкий–средний | Хотим dark mode + консистентность без переписывания |
| **C. Точечная замена (high-value)** | Заменить там, где kit строго лучше: таблицы отчётов → `B24Table`; модалки → `B24Modal`/`useOverlay`; `alert()` → `useToast`; `Empty/Skeleton/Pagination`. Бренд-каркас оставить кастомным | средняя | средний | **Лучший ROI**: ощутимая польза, бренд сохранён |
| **D. Полный ре-скин под нативный Bitrix** | Заменить весь `ms-*` на B24, принять «Air»-вид, отказаться от бренда | высокая (недели) | высокий | Только если «нативный вид Bitrix» — жёсткое требование |

## 6. Грубая оценка трудозатрат (T-shirt)

- **A** — околонулевая, размазана по разработке.
- **B** — S–M: один проход по `main.css` (маппинг токенов) + проверка светлой/тёмной.
- **C** — M: таблицы отчётов (рекурсивные — самое дорогое), модалки, тосты, empty/skeleton/pagination; нужен визуальный QA в iframe.
- **D** — L (многонедельная): 49 файлов + кастомные таблицы/канбан/embedded + полный визуальный QA + воспроизведение бренда поверх kit. Высокий риск регрессий без авто-визуальных тестов.

## 7. Что должно определить выбор (ключевые драйверы)

1. **Зачем мигрируем?** Нативный вид / тёмная тема / доступность / снижение поддержки / скорость разработки — каждый драйвер ведёт к разному варианту.
2. **Бренд (лайм/градиент) — священен или обсуждаем?** Если священен → D отпадает, путь B/C.
3. **Аппетит к визуальному риску на embedded-экране** (его видят пользователи чаще всего).
4. **Готовность включать тёмную тему** (это отдельный объём по аудиту кастома).

## 8. Рекомендация (под зафиксированные драйверы)

Драйверы — **нативный вид + a11y/UX + меньше CSS**, бренд **отпускаем**. Это вариант **D (полная миграция на нативный «Air»-вид)**, реализованный **B+C-методами** (фундамент на токенах, точечные замены там, где kit лучше) и **строго фазами**. Поскольку бренд не воспроизводим — отпадает самая дорогая часть D; остаётся объём (49 файлов) и риск визуальных регрессий (авто-тестов нет → компенсируем чек-листом).

### 8.1. Рекомендуемый фазированный путь (оценочно, реализация — отдельным решением)

1. **Фаза 0 — подготовка (S).** Зафиксировать точную версию kit (`2.5.3`), включить нужную тему (light/edge; опц. dark), собрать визуальный чек-лист ключевых экранов (особое внимание `embedded.vue`). Снять «до»-скриншоты.
2. **Фаза 1 — фундамент / токены (S–M).** Убрать фирменные переопределения из `main.css` (лайм/градиент/скругления), перевести базу на токены «Air». Тут приложение принимает нативный вид. Включить `app.config.ts → b24ui` как точку глобальной темизации.
3. **Фаза 2 — каркас страниц (M).** Шеллы/шапки/поверхности (`ms-page-shell/header/surface/panel`) → `B24Container`/`B24Page*`/`B24Card`/`B24SidebarLayout`. По странице за раз.
4. **Фаза 3 — high-value компоненты (M, наибольшая польза).** Таблицы отчётов → `B24Table` (получаем сорт/пагинацию/виртуализацию/a11y); модалки → `B24Modal`+`useOverlay`; `alert()` → `useToast`; пустые состояния/лоадеры → `B24Empty`/`B24Skeleton`/`B24Pagination`.
5. **Фаза 4 — формы и остаток (M).** Инпуты/селекты/табы/бейджи/ноты → `B24Input/Select/SelectMenu/Tabs/Badge/Alert`; убрать глобальные input-стили из `ms-page-shell`.
6. **Фаза 5 — `embedded.vue` (S–M, отдельно и осторожно).** Самый частый пользовательский экран и высокий риск; мигрировать последним, с тестом в реальном iframe Bitrix.
7. **Фаза 6 — чистка (S).** Удалить из `main.css` оставшиеся неиспользуемые `ms-*`, финальный визуальный проход, опц. включить тёмную тему и проверить.

**Сквозные правила:** по странице/компоненту за раз, каждый шаг — отдельный коммит + проверка в iframe; `embedded.vue` — последним; ничего не выпиливать из `ms-*`, пока класс используется.

### 8.2. Грубый размер и риск

- Суммарно — **L (несколько недель календарно при инкрементальном темпе)**, но риск управляем за счёт фазовости: каждая фаза самостоятельна и обратима.
- Самые ценные фазы (1, 3) дают видимый эффект рано: нативный вид + лучшие таблицы/тосты/доступность.
- Узкие места: рекурсивные таблицы отчётов (Фаза 3), `embedded.vue` (Фаза 5), отсутствие авто-визуальных тестов (компенсируем скриншот-чек-листом).

### 8.3. Открытые вопросы перед стартом реализации

- Включаем ли **тёмную тему** сразу (Фаза 1) или после полной миграции? (Влияет на объём проверок.)
- Нужен ли **минимальный визуальный регресс-харнесс** (хотя бы скриншоты ключевых экранов) до старта — рекомендуется.
- Порядок страниц в Фазах 2–4: начать с «лёгких» отчётов для отладки паттерна, оставить сложные (project-task, доска) на потом.

## Приложение. Сопоставление `ms-*` → B24 (кратко)

- **Прямая замена:** таблицы (`ms-table*` → `B24Table`), модалки (`ms-modal-*` → `B24Modal`+`useOverlay`), empty (`ms-empty-state` → `B24Empty`), pill/note (`ms-pill`/`ms-note*` → `B24Badge`/`B24Alert`), формы, pagination/progress/skeleton/tooltip, табы (`ms-tabbar` → `B24Tabs`).
- **Частично (компонент есть, но бренд/радиус — кастом):** surfaces/cards (`B24Card`/`B24PageCard` + ручной радиус), гриды (`B24PageGrid/Columns`), типографика/шапка (`B24PageHeader`).
- **Остаётся кастомом:** `ms-page-shell` (градиент+лайм), `ms-surface-hero`, `ms-eyebrow`, лаймовые активные сегменты, KPI/Stat-карточки, code-block.

**Ключевые файлы:** `app/assets/css/main.css` (42 `ms-*`), `app/app.config.ts` (ключ `b24ui`), `nuxt.config.ts` (`colorMode`), `app/components/reports/*.vue` + `app/pages/**/*.client.vue` (потребители `ms-*`, особенно таблицы отчётов), `app/pages/embedded.vue` (высокий риск, частый экран).

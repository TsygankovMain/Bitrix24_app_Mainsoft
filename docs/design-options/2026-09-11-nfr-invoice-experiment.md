# Эксперимент на nfr-mainsoft: смарт-счёт и акт через REST

Дата: 11.09.2026. Портал: `nfr-mainsoft.bitrix24.ru` (тестовый, тариф `ru_nfr` — NFR, партнёрская лицензия, коммерческий).
Контекст: [варианты «Счёт и акт по трудозатратам»](2026-09-11-invoice-act-options.md), вариант Б.

> **Статус: живая часть эксперимента не выполнена — нет рабочего доступа на запись.**

> статическая схема полей, документация) и что нужно, чтобы довести проверку до конца.

## 1. Цель

Проверить на живом портале, что приложение «Учёт трудозатрат» может через REST:

- создать новый смарт-счёт CRM (`entityTypeId 31`) с товарными строками «часы × ставка» без товаров каталога;
- напечатать по нему штатным генератором документов счёт и **отдельный акт** с тем же номером и датой;
- понять, кто нумерует счёт и как номер попадает в акт;
- понять, какие scope нужны приложению.

## 3. Результаты по пунктам

### 3.1. Scope и доступность методов

**Ключ Вайбкода.** В `/v1/me` у ключа заявлены scope, среди них `crm`, `catalog`, `documentgenerator`, `sale`, `disk`, `user`, `task`. Но это права ключа, а фактических токенов портала нет — вызвать `crm.item.*`, `crm.item.productrow.*`, `crm.documentgenerator.*` через него нельзя (`TOKEN_MISSING`).

**Приложение «Учёт трудозатрат» на nfr** (`app.info`: `ID 116`, `CODE local.6a9c82aa24d047.81533714`, `STATUS L` — локальное, `LICENSE ru_nfr`, `INSTALLED false`):

```
scope → crm, user_brief, task, sonet_group, userfieldconfig, placement,
        user.userfield, entity, tasks, tasks_extended
```

- `crm` есть — этого хватает на `crm.item.*` (в т.ч. `entityTypeId 31`), `crm.item.productrow.*` и `crm.documentgenerator.*` (CRM-обёртка генератора живёт в scope `crm`, см. 3.5).
- `documentgenerator` нет — методы `documentgenerator.template.*` / `documentgenerator.document.*` (генератор со своим REST-провайдером данных) приложению недоступны.
- `catalog` нет — нельзя читать ставки НДС (`catalog.vat.list`) и единицы измерения (`catalog.measure.list`).
- Расхождение с кодом: в `.env.example` приложения `SCOPE=crm,user_brief,pull,placement,userfieldconfig,imopenlines`, а у установленного на nfr приложения `pull` и `imopenlines` нет, зато есть `task`, `tasks_extended`, `sonet_group`, `entity`. Права выданы по настройкам локального приложения на портале, а не по `.env`.
- `INSTALLED false` у локального приложения дев-стенда — установка на портале формально не завершена (не вызывался `installFinish`). На работу REST по токену это не влияет, но стоит проверить отдельно.

### 3.2. Поля смарт-счёта (статическая схема, не живой `crm.item.fields`)

Из `GET /v1/guide` (сущность `invoices` = `crm.item.*` с `entityTypeId 31`, scope `crm`):

| Назначение | Поле | Примечание |
|---|---|---|
| Компания клиента | `companyId` | number |
| Контакт-плательщик | `contactId` | number |
| Наша компания | `mycompanyId` | number, компания с флагом «моя компания» |
| Привязка к сделке | `parentId2` | в статической схеме нет (динамическое поле связи), по apidocs — есть |
| Даты | `begindate` (дата счёта), `closedate` (срок оплаты) | хранятся без времени |
| Стадия, воронка | `stageId` (`DT31_<воронка>:<код>`), `categoryId` | стадии портальные, брать из `crm.status.list` c `ENTITY_ID = SMART_INVOICE_STAGE_<воронка>` |
| Валюта, сумма | `currencyId`, `opportunity`, `isManualOpportunity` | без `isManualOpportunity = Y` сумма считается по строкам |
| НДС | `taxValue` (по apidocs), ставка — в товарных строках `taxRate`, `taxIncluded` | |
| Номер | `accountNumber` | string, не только чтение — см. 3.6 |
| Прочее | `title`, `comments`, `assignedById`, `xmlId`, `sourceId`, `opened`, `isRecurring` | |

Живой `crm.item.fields` (с подписями, пользовательскими полями и списком обязательных на nfr) **не получен**.

### 3.3. Тестовая компания-клиент и «моя компания»

**Не выполнено** — нет доступа на запись и чтение CRM. Компании не создавались.

### 3.4. Смарт-счёт с товарными строками

**Не выполнено.** По документации схема такая:

1. `crm.item.add` (`entityTypeId 31`): `title`, `companyId`, `mycompanyId`, `currencyId`, `begindate`, `closedate`, `parentId2`.
2. `crm.item.productrow.set` (`ownerType = "SI"`, `ownerId = <id счёта>`, `productRows[]`): `productName`, `price`, `quantity`, `measureCode`/`measureName`, `taxRate`, `taxIncluded`, скидка. `productId` необязателен — строка без товара каталога допустима. В обёртке Вайбкода (`PUT /v1/invoices/:id/products`) список полей строже, `measureCode` там не заявлен.
3. Перечитать `crm.item.get` и `crm.item.productrow.list` — сумма, номер, строки, НДС.

Ловушка из Вайбкода: товарные строки — отдельный ресурс, в теле счёта не записываются; `productrow.set` заменяет весь список, изменённая строка получает новый `id`.

### 3.5. Генератор документов

**Не выполнено** — список шаблонов на nfr не получен, документы не генерировались.

Что известно по документации (apidocs.bitrix24.ru, раздел [crm/document-generator](https://apidocs.bitrix24.ru/api-reference/crm/document-generator/index.html)):

| Что | Метод, поля |
|---|---|
| Две ветки генератора | `crm.documentgenerator.*` — scope **`crm`**, документ строится по `entityTypeId` + `entityId`, метки заполняются данными CRM. `documentgenerator.*` — scope `documentgenerator`, провайдер `providerClassName` + произвольный `value`, данных CRM не видит. Приложению нужна первая ветка — **её scope `crm` у приложения уже есть** |
| Список шаблонов | `crm.documentgenerator.template.list`, фильтр по `entityTypeId` (для смарт-счёта `31` или `31_category_<воронка>`), `region`, `active`, `code`, `numeratorId`. В ответе `id, name, region, code, numeratorId, entityTypeId, withStamps, download` |
| Свой шаблон | `crm.documentgenerator.template.add`: `file` (`["имя.docx", base64]`), `name`, `numeratorId`, `region`, `entityTypeId` — **массив**, шаблон можно привязать сразу к нескольким типам (например, и к смарт-счёту, и к сделке), `users`, `code` |
| Документ | `crm.documentgenerator.document.add`: `templateId`, `entityTypeId`, `entityId`, `values`, `stampsEnabled`, `fields`. В `values` можно переопределить любую метку, в т.ч. **`DocumentNumber`** |
| Готовность | PDF собирается асинхронно: сразу после `add` `pdfUrl` может не быть, повторять `crm.documentgenerator.document.get` через 30–40 с. Признаки ошибки конвертации в полях документа |
| Ссылка клиенту | `publicUrl` изначально `null`, включается `crm.documentgenerator.document.enablepublicurl` |
| Метки номера и даты | Стандартные метки документа — `DocumentNumber`, `DocumentCreateTime`, `DocumentTitle` (`crm.documentgenerator.template.getfields`). Точные имена меток полей самого смарт-счёта (номер счёта, дата счёта) по документации не установлены — их отдаёт `template.getfields` по реальному шаблону |
| Штатные «Счёт» и «Акт» | Справка ([helpdesk 18089278](https://helpdesk.bitrix24.ru/open/18089278/)) говорит только, что на портале есть набор стандартных шаблонов «для счетов, актов, КП». Привязан ли штатный «Акт» к смарт-счёту на nfr — **не проверено** |

Использовать штатный шаблон акта сделки для счёта напрямую нельзя: шаблон работает с тем типом, к которому привязан. Можно выгрузить его DOCX (`download` из `template.list`) и завести копию с `entityTypeId: [31]` через `template.add` — но метки сделки и счёта различаются, копию придётся править.

### 3.6. Нумерация

**Не проверено вживую.**

Здесь два независимых номера:

- **Номер счёта** — поле `accountNumber` смарт-счёта. Оно не только для чтения. Присваивает ли его нумератор счетов портала сам при `crm.item.add` и принимает ли REST номер вручную, документация прямо не говорит.
- **Номер документа** генератора — у каждого шаблона свой нумератор (`numeratorId`, методы `crm.documentgenerator.numerator.add/list`, формат с `{NUMBER}`, счётчик, период сброса). Несколько шаблонов могут делить один нумератор.

Как получить «номер акта = номеру счёта»:

1. **Передавать номер явно:** `document.add` с `values: {DocumentNumber: <accountNumber счёта>}` — по документации метка переопределяется. Самый прямой путь, но надо проверить, что переопределённый номер попадает и в документ, и в поле `number`.
2. **Метка поля счёта в шаблоне акта:** в DOCX акта вместо `{DocumentNumber}` поставить метку номера счёта из провайдера смарт-счёта, а дату — меткой даты счёта (`begindate`). Тогда номер и дата акта всегда совпадают со счётом без участия приложения.
3. Общий нумератор для шаблонов «Счёт» и «Акт» — **не подходит**: общий счётчик выдаст акту следующий номер, а не тот же.

Живой проверки ни одного варианта нет.

### 3.7. Ограничения

- Ключ Вайбкода `vibe_app_*` без сессии бесполезен для работы с данными портала. Для headless-скриптов нужен личный ключ `vibe_api_*` или вебхук.
- Токен приложения живёт час, refresh одноразовый и общий для дев- и демостенда — для экспериментов со стороны его брать нельзя.
- Тариф nfr — NFR (коммерческий), CRM и генератор документов на нём доступны (по тарифу, вживую не проверено).

## 5. Выводы для проектирования

Все выводы — по документации и правам приложения, без живого подтверждения.

1. **Scope.** Для счёта, товарных строк и печати через `crm.documentgenerator.*` достаточно уже выданного `crm`. `documentgenerator` не нужен. `catalog` нужен только если брать ставки НДС и единицы измерения из портала — иначе держим их в настройках приложения и переустановка не нужна. Заодно стоит привести `SCOPE` в `.env.example` в соответствие с тем, что реально выдано на портале (сейчас там `pull`, `imopenlines`, которых у приложения нет).
2. **Как печатать акт.** Рекомендуемый путь — **свой шаблон «Акт выполненных работ» для смарт-счёта** (`template.add` с `entityTypeId: [31]`), где номер и дата — метки полей самого счёта. Приложение генерирует документ `document.add` по счёту, дожидается `pdfUrl` фоновым опросом и при необходимости включает публичную ссылку. Штатный шаблон акта использовать, если он окажется привязан к смарт-счёту на портале клиента, — проверить на nfr.
3. **Нумерация.** Источник правды — `accountNumber` счёта (нумератор счетов портала). Акт своего номера не заводит: либо метка номера счёта в шаблоне, либо `values.DocumentNumber = accountNumber` при генерации. Общий нумератор для счёта и акта не использовать.
4. **Надёжность.** После `crm.item.add` и `productrow.set` перечитывать счёт и строки; сумма при `isManualOpportunity = N` считается по строкам.

## 6. Что осталось непроверенным и как довести

Непроверено всё, что требует записи или чтения CRM: пункты 3.3–3.6 целиком и живой `crm.item.fields`. Ключевые вопросы:

- создаётся ли строка без товара каталога с единицей «ч» (`measureCode`/`measureName`) и НДС;
- кто и когда присваивает `accountNumber`, можно ли задать его по REST;
- какие шаблоны для `entityTypeId 31` есть на nfr, есть ли среди них «Акт»;
- переопределяется ли `DocumentNumber` через `values` и какие метки номера и даты счёта отдаёт `template.getfields`;
- сколько ждать PDF на nfr.

Чтобы довести эксперимент (20–30 вызовов), нужен один из доступов на nfr, явно выданный на эту задачу:

1. **Входящий вебхук nfr** со scope `crm` (и `catalog` для ставок НДС) — самый простой вариант; или
2. **Личный ключ Вайбкода** `vibe_api_*` для nfr; или
3. Разрешение писать тестовые данные **токеном самого приложения** — это заодно проверит ровно те права, с которыми будет работать приложение. Только без refresh: брать токен, пока он живой.
